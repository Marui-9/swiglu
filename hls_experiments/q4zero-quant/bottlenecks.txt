Bottleneck Analysis — K_WV=16 Parallel REDUCE, MAX_BATCH=4, actual_tokens
=============================================================================
Date: 2026-05-24  |  Based on: csynth.rpt (May 24) + Vivado implementation
HLS: 87,611 LUTs (74%), 246 DSP (19%), 282 BRAM (97%), 159K FF (67%), 32 URAM (50%)
Vivado: 107,948 LUTs (92.2%), routes and closes timing at 250 MHz, no violations
MAC_ALL: II=1 at 16 chains (260 cycles, 16 DSP) — ZU5EV ceiling broken
Decode: 3.49M cycles, 3.00 t/s.  Prefill (B=4): 2.18M/token, 3.81 t/s.


1. DDR Load Bandwidth — 35% of Decode Cycles, Saturated
---------------------------------------------------------
Weight load phases consume 1.22M of 3.49M decode cycles (was 1.72M of 3.99M at
K_WV=12). Both WV and output ports operate at 128 bits/cycle (97.5% of 4 GB/s).

  WV load:   1,430 cyc/iter × 512 iter = 0.73M (21% of decode total)
  Out load:  470 cyc/MG × 8 MG × 256 iter = 0.96M (27% of decode total)
  Combined:  1.69M (48% of decode — the largest single consumer)

At actual_tokens=4, DDR load amortized: per-token DDR drops to 0.42M (19%).
The load-then-compute pattern means every decode call pays the full DDR cost.

Attempted fix: overlapping weight pre-load with MAC via HLS DATAFLOW. Works
architecturally (3.13M cycle proof-of-concept) but HLS duplicates hardware
inside DATAFLOW → 149K LUTs. Not viable on ZU5EV without RTL-level control.


2. LUT Budget — 92.2%, the Binding Resource Constraint
--------------------------------------------------------
Vivado LUTs at 108K of 117K. Headroom: 9K (7.8%). This is the primary resource
ceiling. The K_WV=16 MAC_ALL achieves II=1 at 16 chains — the long-sought ZU5EV
ceiling — but at 92.2% LUT utilization, further K_WV increases are unlikely.

DSP (8.2%), URAM (50%), and LUTRAM (13.3%) have massive headroom but cannot
substitute for routing LUTs. The load-function AXI address computation and
16-way LOAD_NIB demux dominate LUT usage.

Key LUT-saving techniques applied:
  - CPU pre-converted d values: eliminated float→fixed converters (−29K Vivado)
  - Parallel REDUCE (no DATAFLOW): avoids control set inflation
  - Narrow fxd_scale_t (18-bit): single-DSP multiplies, no cascades

BRAM at 91.7% is also tight — 16 nib_r arrays × 2 instances = 128 BRAM_18K
for nibble storage, plus X1/X2 caches and output BRAM tiles. Only 12 BRAM free.


3. K_WV Scaling — The Ceiling Is Reached
------------------------------------------
  K_WV=12: 101K LUTs, 683 iter, 2.63 t/s decode, 3.44 prefill
  K_WV=13: 97K LUTs, 631 iter, 2.78 t/s (routing anomaly: LUTs dropped)
  K_WV=14: 101K LUTs, 586 iter, 2.81 t/s
  K_WV=16: 108K LUTs, 512 iter, 3.00 t/s decode, 3.81 prefill

The LUT-vs-K_WV curve is non-monotonic (K_WV=13 had lower LUTs than K_WV=12)
but the trend beyond K_WV=14 is clear: each additional chain adds ~3.5K Vivado
LUTs. K_WV=17 would project to ~112K LUTs (95.7%) — very tight but technically
possible. K_WV=18 would exceed 117K.

K_WV=16 is the practical maximum: it's a power of 2 with clean iteration count
(8,192/16=512, no padding) and delivers the 3.0 t/s milestone.


4. Output Path — 44% of Decode, DDR-Dominated
-----------------------------------------------
compute_output consumes 1.54M cycles (44% of decode — up from 39% at K_WV=12
because the X1/X2 phase shrank more). Within it, DDR load dominates at 63%.

K_DOWN=16 was attempted but failed at 130.8K Vivado LUTs. Output time-mux
REDUCE reduced LUTs but added cycles (REDUCE > MAC_MG in this path). The
output path remains the least-optimized phase but has proven hard to improve
without LUT blowup or cycle regression.


5. Token Pipelining — Still Blocked by HLS DATAFLOW
-----------------------------------------------------
Overlapping token N's output with token N+1's compute would reduce per-token
latency from 3.49M to max(1.93M, 1.54M) = 1.93M (45% reduction → ~4.3 t/s).
But HLS DATAFLOW requires each process to run to completion before the next
can consume its output. Full pipeline duplication (2× hardware → ~216K Vivado)
is the only HLS path. Not viable.


6. Amdahl's Law — CPU Overhead
--------------------------------
CPU overhead ~125 ms/token (attention, norms, embedding, sampling, driver).

  Decode at 3.00 t/s:   213 ms FPGA + 125 ms CPU = 338 ms → 2.96 t/s effective
  Prefill at 3.81 t/s:  168 ms FPGA + 125 ms CPU = 293 ms → 3.41 t/s effective

Theoretical max at infinite FPGA speed: 1/0.125 = 8.0 t/s.
Each incremental FPGA improvement yields diminishing returns due to the fixed
CPU component. The CPU overhead is now the next bottleneck to attack.


7. Resource Mismatch — Abundance Can't Help Scarcity
------------------------------------------------------
DSP (8.2%), URAM (50%), and LUTRAM (13.3%) have massive headroom but are
structurally mismatched to the actual bottleneck: LUT-based routing. The
16-way nibble mux, AXI address computation, and pipeline registers consume
LUTs that cannot be substituted with DSPs or URAM.


Summary — Bottleneck Ranking
-----------------------------
  Rank  Bottleneck                    Impact             Status
  ─────────────────────────────────────────────────────────────────────
  1.    LUT budget                    92.2% used         K_WV=16 ceiling reached
  2.    BRAM budget                   91.7% used         Tight, 12 free
  3.    DDR load bandwidth            48% of cycles      Saturated at 128b/cyc
  4.    Output path DDR load          27% of cycles      Port saturated
  5.    Amdahl CPU overhead           125 ms/token       Next bottleneck
  6.    Token pipelining              45% possible gain  HLS DATAFLOW limitation
  7.    K_WV scaling beyond 16        ~3.5K LUTs/chain   K_WV=17 possible? (95.7%)

The design reaches 3.0 t/s decode and 3.81 t/s prefill on ZU5EV — the
practical ceiling for Q4_0 HLS SwiGLU acceleration on this device.
Further gains require: larger device (ZU7EV), RTL-level optimization,
or system-level changes (CPU overhead reduction, speculative decode).
