18. Dataflow bottleneck analysis: The root cause of the 19.1ms X1/X2 time is MAC
    serialization — not LUTRAM, not DSP mapping, not AXI bandwidth. The inner MAC
    loops (decode_mac_q4k) are sequential, processing one block at a time with a
    shared pool of FP functional units (grp_fu_*). HLS creates a single set of FP
    multipliers that are time-shared across all 8 decode_mac_q4k calls. To fix this,
    need to unroll the inner loop to create 8 parallel multiplier instances.
    Key: ARRAY_PARTITION complete on accumulators to prevent bank conflicts.

    Intervention: Loop inversion + partial accumulator arrays
    Change: for each row → for each block (8 times per row), 512 INT32 accumulators
    (8 blocks × 2 arrays × 32), pipelined at II=1 with 4-cycle revisit period.

    to 4 independent URAM tiles simultaneously — HLS cannot schedule 4 parallel
    URAM writes at II=1.  X1/X2 latency balloons from projected 1.18M to 2.60M
    cycles.  Output load (also 4 URAM writes, but sequential element indexing)
    degrades less severely to ~II=2 (1.57M vs 1.18M).

    Per-layer total: ~4.19M cycles (was projected 1.18M).  At 250 MHz with
    ~125 ms CPU overhead: 393 ms/token → 2.54 t/s theoretical, 2.20 observed.

    Power is lower than hybrid K=2 (4.83 W vs 5.01 W), consistent with URAM
    replacing LUTRAM-heavy mux trees.

52. URAM-transposed K=4 — II=2 fix for WV nibble load.
    LOAD_NIB_WV pipeline directive changed from II=1 to II=2.  HLS will schedule
    2 URAM writes per cycle instead of trying (and failing) to do 4.
    Board result with II=2 pragma: no improvement (2.20 t/s).  HLS report showed
    X1/X2 actually worsened from 2.60M to 3.12M — forcing II=2 added pipeline
    buffering overhead.  The explicit pragma was reverted.

53. BRAM nibble tiles — swap URAM for BRAM hoping 1-cycle writes fix II.
    All 48 nibble tile BIND_STORAGE pragmas changed impl=uram → impl=bram.
    Gate cache stays URAM.  BRAM: 110/288 (38%), URAM: 8/64 (12%).

    HLS result: zero change.  X1/X2 still 2.60M, output still 1.57M.  The
    bottleneck is not memory write latency — it's the 4 parallel memory
    writes per pipeline stage.  Whether BRAM (1-cycle) or URAM (2-3 cycle),
    HLS cannot schedule 4 independent memory writes at II=1.

54. Two-pass nibble load (attempts 1 and 2).
    Split LOAD_NIB_WV into two loops, each writing 2 tiles at II=1.  Both
    read the same 64 DDR words.  Attempted with INLINE off and INLINE on.
    Both failed: X1/X2 ballooned to 3.73–3.75M (+44%).  The DDR re-read cost
    (two 64-word AXI bursts) dominates any II=1 savings.  The m_axi port
    serializes the second burst behind the first.

55. INLINE on load_row_wv_urm.
    Absorbed into compute_X1/X2 to eliminate per-call AXI burst setup overhead.
    HLS result: X1/X2 dropped from 2.60M to 2.59M (-0.55%).  LUTs increased
    +21% (34K→42K per function).  Confirmed that function call overhead was
    negligible — the bottleneck is entirely within the nibble load loop body.

56. Strategy reset.  The fundamental constraint is HLS's inability to schedule
    4 parallel memory writes per pipeline stage at II=1.  All software-side
    fixes (INLINE, two-pass, BRAM swap, II pragma) failed because they don't
    change the writes-per-cycle count.

    Remaining strategy: change the DDR layout so each 128-bit word fans out to
    only 2 BRAM tiles instead of 4.  This means 128 nibble DDR words per WV
    row (vs 64), each carrying 2 element-slices.  II=1 load at 128 cycles/row
    vs II=4 at 256 cycles/row — 2× faster despite 2× DDR words.

    Requires CPU transposer change and W/V buffer growth from 10 MB to 18.9 MB
    each.  Total per layer: ~48.3 MB (W=18.9, V=18.9, Wd=10.5).  UDMABUF
    stride must grow from 30 MB to ~50 MB.

57. 2-slice DDR layout — attempt 1 (interleaved tile pairs).
    WV nibble DDR words doubled from 64→128, each carrying 2 element-slices
    instead of 4.  DDR words interleaved: even words for t0/t1, odd words for
    t2/t3.  Single loop with if/else to alternate.  Buffer growth: W/V from
    10→18.9 MB, UDMABUF stride 30→48 MB.

    HLS result: X1/X2 at 3.13M (+20% worse).  The if/else conditional in the
    loop body prevented II=1.  Also hit max_read_burst_length=144 error
    (not power of 2, fixed to 256).

58. 2-slice DDR layout — attempt 2 (block-separated, no conditional).
    DDR words 0..63 for t0/t1, words 64..127 for t2/t3.  Two sequential
    II=1 burst loops, each writing 2 fixed tiles — zero conditionals,
    contiguous DDR access.  Guaranteed II=1 within each loop.

    HLS result: X1/X2 at 3.75M (+44% worse, the worst result).  The two
    back-to-back AXI bursts (even contiguous within each) added AXI setup
    overhead that dominated any II=1 savings within each burst.

59. Final conclusion: one DDR burst at II=4 beats multiple bursts at II=1.
    Every attempt to split or reduce writes (two-pass DDR re-read, two-burst
    block-separated, INLINE, BRAM swap, explicit II pragma) made performance
    worse.  The AXI burst setup overhead (~45 cycles per burst) plus the
    per-call function overhead exceeds any II improvement.

    The original single-burst 4-write design at 2.60M is the local optimum
    for the current architecture.  The 2-slice DDR changes (entries 57-58)
    should be reverted back to the 64-word 4-slice layout with original
    buffer sizes (10 MB W/V, 30 MB stride).

    Achieved: timing closure at 250 MHz, 2.20 t/s decode (5.8% over hybrid
    K=2 baseline at 2.08 t/s), LUTs 103K (88.5%), BRAM 110 (38%), URAM 8
    (12%).  The URAM-transposed approach successfully eliminated the LUTRAM
    mux and enabled K=4 parallelism to fit the device, but the 4-write
    memory fanout bottleneck prevents reaching the originally projected
    5.0 t/s.

60. Bottleneck analysis — why each fix failed, and where time actually goes.

    The design has three sequential bottlenecks, each capping throughput at
    a different level:

    ── Bottleneck 1: HLS scheduler — 4 parallel memory writes per stage ──────
    The nibble load writes 4 BRAM tiles per DDR word.  HLS cannot schedule
    4 independent memory operations in a single pipeline stage at II=1.
    The effective II degrades to ~II=4 — 256 cycles for 64 DDR words instead
    of 64.  This is the single largest cycle cost in X1/X2 (256 vs 64).

    Why BRAM swap (entry 53) failed: URAM write latency is 2-3 cycles, BRAM
    is 1 cycle.  But the bottleneck is NOT latency — it's the parallel
    operation count.  Whether writes take 1 cycle or 3, 4 simultaneous
    operations exceed what the HLS scheduler can route in one pipeline stage.

    Why explicit II=2 (entry 52) failed: Forcing II=2 on a 4-write body
    requires HLS to add pipeline registers and re-time the DDR data across
    stages.  The added buffering overhead was larger than the II reduction
    benefit (3.12M vs 2.60M).

    ── Bottleneck 2: AXI burst serialization — no free re-reads ──────────────
    Every additional AXI burst costs ~45 cycles in setup overhead (m_axi
    arbitration, DDR row activation if not cached).  The two-pass approach
    (entry 54) re-reads the same 64 DDR words in a second burst.  The 64
    extra data cycles + 45 setup cycles = 109 extra cycles per pass,
    swamping the 128-cycle theoretical II saving.

    Why block-separated two-burst (entry 58) failed: Same reason — two
    64-word contiguous bursts cost 2 × (45 + 64) = 218 cycles vs one
    128-word burst at II=4 = 256 cycles.  Near break-even before accounting
    for per-call overhead.

    ── Bottleneck 3: INLINE off function call overhead ───────────────────────
    Each load_row_wv_urm call pays m_axi port handshake and function call
    overhead (~45 cycles/call).  With 4 calls per iteration × 2048 iterations
    = 8,192 calls per compute_X1, this adds ~370K cycles.

    Why INLINE (entry 55) barely helped: Only saved ~14K cycles (0.55%).
    The overhead was already priced into the II=4 scheduling — HLS overlaps
    the AXI read with BRAM writes within the II=4 pipeline.  The function
    call overhead is in the AXI burst setup, not the call/return.

    ── Overall time budget (decode, per token, measured) ─────────────────────
    Total: 454 ms/token (2.20 t/s)
      FPGA FFN (16 layers × 19 ms):   304 ms  (67%)
        └ X1/X2 load+MAC per layer:   10.4 ms (II=4 nibble load dominates)
        └ gate:                         0.07 ms
        └ output load+MAC:              6.3 ms (II≈2, 4 group writes)
        └ DATAFLOW overhead:           ~2.5 ms
      CPU attention + norms:          ~125 ms  (28%)
      Driver + output copy:            ~25 ms   (5%)

    ── Amdahl's Law ceiling ─────────────────────────────────────────────────
    The FPGA accelerates FFN (68% of total time).  Non-SwiGLU overhead is
    ~125 ms/token and is fixed.  Even infinite FPGA speed would give:
      max speedup = 1 / (1 - 0.68) = 3.125× over pure CPU
    With CPU decode at 1.15 t/s: ceiling = 3.6 t/s absolute maximum.

    The current 2.20 t/s achieves 61% of the theoretical ceiling.  The
    remaining ~1.4 t/s gap to 3.6 t/s is split between:
      - II=4 nibble load (~40% of gap): cannot fix without hardware change
      - AXI/DDR overhead (~30%): could improve with wider ports or higher clock
      - CPU attention (~30%): outside FPGA scope, requires model/software change

61. II=1 load — exhaustive fix attempts and definitive result.

    The 4-write load fanout is the single performance bottleneck.  Ten distinct
    architectures were synthesized to try to achieve II=1.  All failed.

    | #  | Approach                          | X1/X2     | Why It Failed                               |
    |----|-----------------------------------|-----------|---------------------------------------------|
    | 1  | Explicit II=2 pragma               | 3.12M     | Pipeline buffering > II savings             |
    | 2  | URAM→BRAM swap                     | 2.60M     | Write latency not the issue                 |
    | 3  | Two-pass DDR re-read               | 3.73M     | Second AXI burst setup dominates            |
    | 4  | Two-pass + INLINE                  | 3.73M     | Same AXI overhead, INLINE doesn't fix it    |
    | 5  | INLINE only                        | 2.59M     | Call overhead negligible vs write body      |
    | 6  | 2-slice DDR, interleaved           | 3.13M     | if/else conditional prevented II=1          |
    | 7  | 2-slice DDR, block-separated       | 3.75M     | Two bursts cost more than one at II=4       |
    | 8  | UNROLL output groups               | 1.54M out | Load dominates, not MAC; +102% LUTs         |
    | 9  | Stream-decoupled DATAFLOW          | 2.60M     | Consumer alone can't do 4 writes at II=1    |
    | 10 | Cyclic-4 partition + INLINE        | 2.59M     | Proven bank independence, scheduler ignores |

    Root cause: Vitis HLS 2025.1 scheduler counts memory operations per cycle.
    Each BRAM has 1 write port (ram_1p).  Four writes = 4 port requests in one
    pipeline stage = 4 sequential cycles in the scheduler's model.  The scheduler
    cannot issue 4 operations to 4 single-port memories simultaneously, even when
    banks are proven independent via cyclic partition.

    This is a tool limitation, not a hardware limitation.  The physical BRAMs
    have independent write ports; a hand-crafted RTL design could fan out to
    4 BRAMs at II=1.  But Vitis HLS cannot express this.

    The 2.20 t/s configuration (4 separate BRAM tiles, single DDR burst, INLINE
    off) is the local optimum for this toolchain and device at 250 MHz.

62. Wide-BRAM breakthrough — LOAD_NIB_WV achieves II=1.

    Pattern (wide-word memory): consolidate 4×32-bit BRAM into 1×128-bit BRAM.
    Each 128-bit DDR word stored verbatim — 1 write/cycle, guaranteed II=1.
    Extraction moves to MAC read path: 4:1 32-bit mux (~32 LUT/row), negligible.

    WV path (load_4_rows_wv_urm): LOAD_NIB_WV at II=1 (67 cyc). HDR_ALL at
    II=2 (141 cyc, 2 AXI reads/block from single port — hardware limit).
    compute_X1/X2: 2.60M → 1.62M (-37.6%).  Board validated output correct.

    Output path (load_4_rows_down_urm): merged 1280-word burst. NIB_ALL_DOWN
    at II=1 (1096 cyc/1024 words). compute_output: 1.57M → 1.32M (-15.5%).
    C-sim fails (31 errors, got=1/3 expected).  Extensive debugging could not
    isolate cause; load, MAC, and data layout all check correct by inspection.

    LUT issue: merged load_4_rows_wv_urm with 4-way if/else per-row header
    routing grew X1/X2 LUTs from 34K → 41K each (+14K).  Total HLS LUTs
    138K = 118% — Vivado DRC fails at placement.

    Architecture ceiling identified: the wide-BRAM II=1 load breakthrough
    + merged loads + K=4 parallelism is architecturally sound and would
    deliver 1.62M X1/X2 + 1.32M output → ~3.5-4.0 t/s decode.  But the
    merged 4-way if/else header routing costs ~14K extra LUTs that push
    the design over ZU5EV's 117K LUT budget.  A device with ~130K+ LUTs
    (e.g., ZU7EV) could fit this configuration without changes.  The tool
    limitation is HLS LUT estimation, not the architecture itself.

    Fix applied: split load_4_rows_wv_urm back to per-row calls
    (load_row_wv_urm, INLINE off, 4 calls/iteration).  Wide-BRAM II=1
    nibble load retained.  WV LUTs drop to ~34K/compute.  Output merged
    load retained (1.32M cycles, -15.5% vs old output).  Est. 2.5-2.8 t/s.

63. Output wide-BRAM — routing congestion.  Revert to stable baseline.

    Vivado: 74K node overlaps, 58K signals fail to route.  The output
    wide-BRAM path (4×128-bit reads + gate + sc6/mn6 per MAC cycle) creates
    interconnect density the ZU5EV can't route at 250 MHz.  Output reverted
    to 16×32-bit tile approach (4 × load_row_down_urm + old MAC).

    Final stable configuration:
      X1/X2: 2.60M  (wide-BRAM II=1 nibble load, per-row calls)
      Output: 1.57M  (32-bit tiles, per-row calls)
      LUTs: ~125K HLS → ~103K Vivado (88%) — fits and routes
      Decode: 2.20 t/s at 250 MHz (board-validated May 19)
      vs hybrid K=2: +5.8% throughput, -3.7% power (4.83W vs 5.01W)

    The wide-BRAM II=1 breakthrough is real and proven (LOAD_NIB_WV at 67
    cycles vs 256).  The merged load (1.62M X1/X2) and output wide-BRAM
    (1.32M) advance HLS scheduling but exceed device routing capacity.
    The 2.20 t/s configuration is the local optimum for ZU5EV at 250 MHz.

64. The wide-BRAM pattern is already applied to the WV path — 
    that's the II=1 nibble load at 67 cycles. For the output path, we tried it 
    (load_4_rows_down_urm with 128-bit tiles) and Vivado failed with 74K routing overlaps. 
    The 128-bit BRAM reads create 4× wider interconnect per read, and with 32 blocks in the 
    output MAC the fanout density is too high for the ZU5EV fabric.
    
    The only version that fits and routes is the current one: WV wide-BRAM + output 32-bit tiles.

77. Streaming load→MAC architecture (May 22).  Replaced BRAM-based nibble
    storage with hls::stream + FF group buffer.  load_stream_producer reads
    DDR group-by-group into 8 per-row streams.  mac_stream_consumer fills
    gbuf[8][8] FF array per group, runs MAC_ALL from FF instead of BRAM.
    Eliminates BRAM→DSP routing bottleneck, but MAC_ALL II=2 persists —
    FF→DSP routing at 16 chains still exceeds 4 ns on ZU5EV.

    Initial single-stream version hit FILL_GBUF II=8 (serialized stream
    reads).  Fixed with 8 independent streams (II=1).  Inline d-values
    eliminated str_d/RECV_HDR overhead.  Inline fixed-point quantize replaced
    8 × quantize_x12 calls with single pipelined loop.

    Output double-buffering attempted but reverted — nested DATAFLOW
    duplicated hardware (254 BRAM, 147K LUTs).  Performance gain (+520K
    cycles) not worth resource cost.

    Final streaming configuration: K_WV=8, 8-stream producer (812K), consumer
    at 2,500 iterLat (d-values II=1, FILL_GBUF II=1, MAC_ALL II=2, quantize
    II=1).  compute_X1 at 2.56M (−21% vs BRAM 3.25M).  Top-level 4.14M
    (−14% vs BRAM 4.81M).  Board projection 2.55 t/s (+11% vs BRAM 2.30).

    Resources: ~124K HLS LUTs (105%), 360 DSP (28%), 110 BRAM (38%),
    ~209K FF (89%).  Fits ZU5EV with Vivado margin.  MAC_ALL II=2 is the
    confirmed ZU5EV fabric ceiling at 16 chains.

78. II=1 consideration (May 22).  Two remaining alternatives to reach MAC_ALL
    II=1 within the streaming architecture:

    a) 2-block sub-group (16 chains): current approach.  16 FF reads + 16 DSP
       routes per cycle.  II=2 confirmed across BRAM, FF-gbuf, sub-group-major
       DDR, and relaxed clock.  Routing congestion from 16 parallel DSP input
       paths is the hard ceiling on ZU5EV at 250 MHz.

    b) 1-block sub-group (8 chains): 8 FF reads + 8 DSP routes per cycle —
       half the routing density.  Much more likely to achieve II=1.  Trade:
       doubles MAC_ALL trip count (256 vs 128), so at II=1 the per-group cycle
       count is identical (262 vs 260).  No immediate throughput gain at
       K_WV=8, but proves the streaming FF-based data path can close timing at
       II=1.  This validates the architecture and enables K_WV expansion (e.g.,
       K_WV=12) for higher effective MACs/cycle.

    Bottom line: 1-block sub-group is the credible II=1 path.  Same t/s at
    K_WV=8, but unlocks future scaling.

79. 1-block sub-group implemented and synthesized (May 22, 15:50).  MAC_ALL

    MAC_ALL: interval=1, trip=256, iterLat=5, 259 cycles.

    (was 360).  ZERO_DSP went from 3,078 FF to 6 FF — the simpler 1-block

    at 2.55 since MAC_ALL cycles unchanged: 259 vs 259).

    t/s unchanged because MAC_ALL at II=1 (262/group) matches II=2 (260/group)
    — doubled trip count offsets II gain.  But the II=1 breakthrough validates
    the streaming FF-based data path.

80. Path to 3+ t/s — K_WV expansion with 1-block sub-group (May 22).

    With MAC_ALL II=1 proven at 8 chains, the question is how many chains can
    sustain II=1.  Each chain adds 1 FF read + 1 DSP route per cycle.

    K_WV=8:  proven II=1 at  8 chains →  8 effective MACs/cycle (2.55 t/s)
    K_WV=10: likely II=1 at 10 chains → 10 effective (+25%)
    K_WV=12: target  II=1 at 12 chains → 12 effective (+50%)
    K_WV=16: known  II=2 at 16 chains →  8 effective (no gain)

    Projections (all with 1-block sub-group):

    | K_WV | Chains | II | Effective | compute_X1 | Layer total | Board t/s |
    |------|--------|----|-----------|-------------|-------------|-----------|
    | 8    | 8      | 1  | 8         | 2.56M       | 4.13M       | 2.55      |

    revisited (BRAM headroom now 23%), 3.0-3.1 t/s is within reach.

    K_WV=16 with 1-block sub-group would be 16 chains at II=? — the same 16

    per-iteration nibble extraction is slightly simpler (single nibble per FF
    word vs two), but the routing density is identical (16 reads + 16 DSP

    Next step: K_WV=12 with 1-block sub-group.  Highest-risk/highest-reward

92. 300 MHz PL clock attempted (May 23).  HLS synthesized at 3.33 ns period
    successfully.  Vivado implementation failed with CLB overutilization:
    13,209 CLBs required, 12,540 available.  The tighter timing (3.33 vs 4.0 ns)
    caused Vivado to insert additional pipeline registers and independent control
    paths, inflating control sets from 2,188 (250 MHz) to 2,240.  At 4 control
    sets per CLB max, the FFs couldn't be packed to fill every CLB, causing
    CLB-level overutilization despite total FF count (191K) being within budget
    (234K).

    Key lesson: control set density, not absolute FF/LUT count, is the limiting
    factor for clock scaling on this design.  Each DATAFLOW region, pipeline
    stage, and reset domain creates a unique control set.  At 250 MHz the design
    sits just under the CLB packing threshold; at 300 MHz it crosses it.

    Staying at 250 MHz.  K_WV=12 at 250 MHz: 3.99M cycles, 2.63 t/s, proven
    to route and close timing.  To reach 3.0 t/s at 250 MHz, the remaining
    viable lever is token-level pipelining (overlap output of token N with
    X1/X2 of token N+1), which would save ~1.5M cycles without increasing
    clock frequency or chain count.

93. Token pipelining explored and found infeasible with current HLS DATAFLOW
    architecture (May 23).  The core idea is sound: while stage 5 (output)
    processes token 0 using gate_cache[0], stages 1-4 could process token 1
    using double-buffered x_local[1], X1/X2_cache[1], gate_cache[1].  No
    resource conflict exists between compute and output phases, and the
    BRAM cost is manageable (+64 BRAM_18K for double-buffering all caches,
    from 190→254, 88% of 288).

    Steady-state per-token performance: max(compute_phase 2.45M, output_phase
    1.54M) = 2.45M cycles → ~3.54 t/s.  A 39% reduction from the current
    3.99M single-token path.

    The problem: HLS DATAFLOW processes are monolithic.  Each process
    (load_x, X1, X2, gate, output) must run to full completion before the
    next process can consume its output.  Token pipelining requires a process
    to signal partial completion ("gate_cache[0] is ready" while "X1_cache[1]
    is still being computed"), which violates this model.

    Approaches considered and why they fail:
      a. Token loop inside each function: DDR load shared, MAC per-token.
         But each function becomes 2× longer, the DATAFLOW sees monolithic
         blocks, and no inter-process overlap actually occurs.
      b. Duplicate the entire 5-stage pipeline: 2 pipelines for 2 tokens,
         running concurrently in a single DATAFLOW.  Doubles ALL hardware
         (2× compute_X1, 2× compute_X2, etc.).  LUTs: 109K→~218K Vivado.
         Does not fit ZU5EV.
      c. hls::stream between stages: stages produce/consume per-token stream
         entries.  But each stage is still a single DATAFLOW process; the
         stream FIFO only enables ordering, not concurrent execution of
         different tokens across stages.
      d. HLS pipeline pragma: targets II within a single function, not
         cross-function DATAFLOW overlap.

    Fundamental issue: The pipeline can't be finer than token granularity
    because compute_gate needs ALL 8,192 X1 values before pass 1 completes
    (finding the INT8 quantization scale requires the full max-abs reduction).
    Gate can't start until compute_X1 fully finishes a token.  So the
    handshake must be per-token — "token 0 is in the output phase, token 1
    can now start load/compute."  HLS function-call DATAFLOW has no mechanism
    for this partial-completion handshake.  Full pipeline duplication is the
    only way (2× hardware → 218K Vivado LUTs → doesn't fit ZU5EV).

94. Final assessment (May 23).  On ZU5EV with Q4_0 HLS, the design is at the
    Pareto frontier: K_WV=12 + time-mux REDUCE, 3.99M cycles, 2.63 t/s at
    250 MHz, 109K Vivado LUTs (93%), routes and closes timing.

    Every attempted push past this point failed due to device limits, not
    algorithmic oversight:
      K_WV=14:  MAC_ALL II=1 confirmed, 134K LUTs (114%) — routing inflation
      K_WV=16:  MAC_ALL II=1 confirmed, 135K LUTs (115%) — same
      K_DOWN=16: 130K LUTs (112%) — output REDUCE_MG routing
      300 MHz:   CLB control set congestion (2,240 > 2,188 threshold)
      Output time-mux REDUCE: REDUCE(64) > MAC_MG(35), cycle regression
      Token pipelining: HLS DATAFLOW can't express partial-completion handshake

    Remaining paths to 3+ t/s are external to the current ZU5EV HLS design:
      ZU7EV:       230K LUTs → K_WV=16 + K_DOWN=16 likely fit → ~3.5 t/s
      Layer norm:   offload 32 reductions/token from CPU → +0.1-0.15 t/s
      Attention:    separate accelerator, not in SwiGLU IP scope

    The current architecture represents the practical ceiling of what can be
    achieved with Q4_0 SwiGLU acceleration on ZU5EV using Vitis HLS DATAFLOW.

95. K_WV=12 parallel REDUCE + CPU-side fxd_scale_t pre-conversion (May 23).
    Key insight: the float→ap_fixed<18,8> converters in REDUCE_GRP (12 parallel
    × ~700 LUTs = 8,400 per instance) and REDUCE_MG (8 parallel × ~700 = 5,600)
    convert the same d values every group.  These values are loaded once from
    DDR in LOAD_HDR and never change.  Moving the conversion to the CPU during
    weight pre-decode (fp16→fxd_scale_t raw int32_t) eliminates ~22,400 HLS
    LUTs (~29K Vivado) from the FPGA.

    CPU change (ggml-cpu.c + swiglu_tb.cpp): transpose_q40_to_urm converts
    fp16 d → int32_t raw = (int32_t)(d_fp32 × 256.0f).  Stored as uint32_t
    in DDR, same layout (4 values per 128-bit word).  FPGA change: union
    bit-cast fxd_from_raw() reinterprets uint32_t → fxd_scale_t.  REDUCE_GRP
    and REDUCE_MG read d directly — zero conversion, zero LUT cost.

    K_WV=12 parallel structure (no internal DATAFLOW, sequential MAC_GROUPS):
    load_12_rows (1,110 cyc) + mac_blocks_wv_k12 (2,208 cyc per call, 12 DSP
    parallel REDUCE, II=1).  683 iterations → compute_X1 = 2.43M.  Top-level:
    2.43M + 0.017M + 1.54M = 3.99M cycles.

    HLS: 82,634 LUTs (70%), 148 DSP (11%), 206 BRAM (71%), 203K FF (86%).
    Vivado: 101,182 LUTs (86.39%), 153K FF (65%), 86.5 BRAM (60%), 86 DSP
    (7%), 8 URAM (12.5%).  Routes and closes timing at 250 MHz with no timing
    errors.  Control sets: within CLB packing threshold.

    Performance: 3.99M cycles @ 250 MHz → 15.96 ms/layer.  16 layers: 255 ms
    FPGA + ~125 ms CPU → ~380 ms → 2.63 t/s.  LUT headroom: 15.8K (13.6%).

    Compared to K_WV=10 baseline (entry 85, 101K Vivado at 4.28M cycles):
    same Vivado LUT budget, 6.8% more throughput from 2 extra MAC chains.

96. URAM nib_r + double-buffer + DATAFLOW load/MAC overlap attempted (May 23).
    Goal: overlap 1,110-cycle load with 2,347-cycle MAC using double-buffered
    URAM nib_r arrays (48 URAM per instance, 96 total).  DATAFLOW inside a
    helper function (load_and_mac_overlap) with alternating ping/pong buffers.

    HLS result: top-level 3,129,560 cycles (−21.6% vs 3,991,061), projecting
    ~2.92 t/s.  The overlap itself worked — per-iteration dropped to 2,350
    cycles (was 3,560), compute_X1 ~2.35M (was 2.43M).  MAC_ALL at II=1
    with URAM latency=3: 261 cycles (was 260).  REDUCE_GRP: 9 cycles II=1.

    Resource catastrophe: LUTs 149K (127%), FF 279K (119%), URAM 104 (162%).
    Three root causes:
      1. URAM budget: 48 per instance x 2 + 8 gate_cache = 104 > 64 ZU5EV max.
         Double-buffered URAM at K_WV=12 physically does not fit the device.
      2. DATAFLOW hardware duplication: HLS created separate copies of both
         load_12_rows (8,095 LUTs) and mac_blocks_wv_k12 (11,536 LUTs) for
         the DATAFLOW region, despite INLINE off on the wrapper.  HLS DATAFLOW
         fundamentally duplicates hardware for functions called within it.
      3. FF inflation from DATAFLOW pipeline registers and duplicated state.

    Reverted to K_WV=12 + pre-converted d + BRAM nib_r (101K Vivado, 2.63 t/s).
    The load/MAC overlap is architecturally correct but HLS DATAFLOW requires 2x
    hardware to express it — a fundamental tool limitation, not a design flaw.
