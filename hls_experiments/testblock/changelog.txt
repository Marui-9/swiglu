18. Dataflow bottleneck analysis: The root cause of the 19.1ms X1/X2 time is MAC
    serialization — not LUTRAM, not DSP mapping, not AXI bandwidth. The inner MAC
    loops (decode_mac_q4k) are sequential, processing one block at a time with a
    shared pool of FP functional units (grp_fu_*). HLS creates a single set of FP
    multipliers that are time-shared across all 8 decode_mac_q4k calls. To fix this,
    need to unroll the inner loop to create 8 parallel multiplier instances.
    Key: ARRAY_PARTITION complete on accumulators to prevent bank conflicts.

    Intervention: Loop inversion + partial accumulator arrays
    Change: for each row → for each block (8 times per row), 512 INT32 accumulators
    (8 blocks × 2 arrays × 32), pipelined at II=1 with 4-cycle revisit period.

    to 4 independent URAM tiles simultaneously — HLS cannot schedule 4 parallel
    URAM writes at II=1.  X1/X2 latency balloons from projected 1.18M to 2.60M
    cycles.  Output load (also 4 URAM writes, but sequential element indexing)
    degrades less severely to ~II=2 (1.57M vs 1.18M).

    Per-layer total: ~4.19M cycles (was projected 1.18M).  At 250 MHz with
    ~125 ms CPU overhead: 393 ms/token → 2.54 t/s theoretical, 2.20 observed.

    Power is lower than hybrid K=2 (4.83 W vs 5.01 W), consistent with URAM
    replacing LUTRAM-heavy mux trees.

52. URAM-transposed K=4 — II=2 fix for WV nibble load.
    LOAD_NIB_WV pipeline directive changed from II=1 to II=2.  HLS will schedule
    2 URAM writes per cycle instead of trying (and failing) to do 4.
    Board result with II=2 pragma: no improvement (2.20 t/s).  HLS report showed
    X1/X2 actually worsened from 2.60M to 3.12M — forcing II=2 added pipeline
    buffering overhead.  The explicit pragma was reverted.

53. BRAM nibble tiles — swap URAM for BRAM hoping 1-cycle writes fix II.
    All 48 nibble tile BIND_STORAGE pragmas changed impl=uram → impl=bram.
    Gate cache stays URAM.  BRAM: 110/288 (38%), URAM: 8/64 (12%).

    HLS result: zero change.  X1/X2 still 2.60M, output still 1.57M.  The
    bottleneck is not memory write latency — it's the 4 parallel memory
    writes per pipeline stage.  Whether BRAM (1-cycle) or URAM (2-3 cycle),
    HLS cannot schedule 4 independent memory writes at II=1.

54. Two-pass nibble load (attempts 1 and 2).
    Split LOAD_NIB_WV into two loops, each writing 2 tiles at II=1.  Both
    read the same 64 DDR words.  Attempted with INLINE off and INLINE on.
    Both failed: X1/X2 ballooned to 3.73–3.75M (+44%).  The DDR re-read cost
    (two 64-word AXI bursts) dominates any II=1 savings.  The m_axi port
    serializes the second burst behind the first.

55. INLINE on load_row_wv_urm.
    Absorbed into compute_X1/X2 to eliminate per-call AXI burst setup overhead.
    HLS result: X1/X2 dropped from 2.60M to 2.59M (-0.55%).  LUTs increased
    +21% (34K→42K per function).  Confirmed that function call overhead was
    negligible — the bottleneck is entirely within the nibble load loop body.

56. Strategy reset.  The fundamental constraint is HLS's inability to schedule
    4 parallel memory writes per pipeline stage at II=1.  All software-side
    fixes (INLINE, two-pass, BRAM swap, II pragma) failed because they don't
    change the writes-per-cycle count.

    Remaining strategy: change the DDR layout so each 128-bit word fans out to
    only 2 BRAM tiles instead of 4.  This means 128 nibble DDR words per WV
    row (vs 64), each carrying 2 element-slices.  II=1 load at 128 cycles/row
    vs II=4 at 256 cycles/row — 2× faster despite 2× DDR words.

    Requires CPU transposer change and W/V buffer growth from 10 MB to 18.9 MB
    each.  Total per layer: ~48.3 MB (W=18.9, V=18.9, Wd=10.5).  UDMABUF
    stride must grow from 30 MB to ~50 MB.

57. 2-slice DDR layout — attempt 1 (interleaved tile pairs).
    WV nibble DDR words doubled from 64→128, each carrying 2 element-slices
    instead of 4.  DDR words interleaved: even words for t0/t1, odd words for
    t2/t3.  Single loop with if/else to alternate.  Buffer growth: W/V from
    10→18.9 MB, UDMABUF stride 30→48 MB.

    HLS result: X1/X2 at 3.13M (+20% worse).  The if/else conditional in the
    loop body prevented II=1.  Also hit max_read_burst_length=144 error
    (not power of 2, fixed to 256).

58. 2-slice DDR layout — attempt 2 (block-separated, no conditional).
    DDR words 0..63 for t0/t1, words 64..127 for t2/t3.  Two sequential
    II=1 burst loops, each writing 2 fixed tiles — zero conditionals,
    contiguous DDR access.  Guaranteed II=1 within each loop.

    HLS result: X1/X2 at 3.75M (+44% worse, the worst result).  The two
    back-to-back AXI bursts (even contiguous within each) added AXI setup
    overhead that dominated any II=1 savings within each burst.

59. Final conclusion: one DDR burst at II=4 beats multiple bursts at II=1.
    Every attempt to split or reduce writes (two-pass DDR re-read, two-burst
    block-separated, INLINE, BRAM swap, explicit II pragma) made performance
    worse.  The AXI burst setup overhead (~45 cycles per burst) plus the
    per-call function overhead exceeds any II improvement.

    The original single-burst 4-write design at 2.60M is the local optimum
    for the current architecture.  The 2-slice DDR changes (entries 57-58)
    should be reverted back to the 64-word 4-slice layout with original
    buffer sizes (10 MB W/V, 30 MB stride).

    Achieved: timing closure at 250 MHz, 2.20 t/s decode (5.8% over hybrid
    K=2 baseline at 2.08 t/s), LUTs 103K (88.5%), BRAM 110 (38%), URAM 8
    (12%).  The URAM-transposed approach successfully eliminated the LUTRAM
    mux and enabled K=4 parallelism to fit the device, but the 4-write
    memory fanout bottleneck prevents reaching the originally projected
    5.0 t/s.

60. Bottleneck analysis — why each fix failed, and where time actually goes.

    The design has three sequential bottlenecks, each capping throughput at
    a different level:

    ── Bottleneck 1: HLS scheduler — 4 parallel memory writes per stage ──────
    The nibble load writes 4 BRAM tiles per DDR word.  HLS cannot schedule
    4 independent memory operations in a single pipeline stage at II=1.
    The effective II degrades to ~II=4 — 256 cycles for 64 DDR words instead
    of 64.  This is the single largest cycle cost in X1/X2 (256 vs 64).

    Why BRAM swap (entry 53) failed: URAM write latency is 2-3 cycles, BRAM
    is 1 cycle.  But the bottleneck is NOT latency — it's the parallel
    operation count.  Whether writes take 1 cycle or 3, 4 simultaneous
    operations exceed what the HLS scheduler can route in one pipeline stage.

    Why explicit II=2 (entry 52) failed: Forcing II=2 on a 4-write body
    requires HLS to add pipeline registers and re-time the DDR data across
    stages.  The added buffering overhead was larger than the II reduction
    benefit (3.12M vs 2.60M).

    ── Bottleneck 2: AXI burst serialization — no free re-reads ──────────────
    Every additional AXI burst costs ~45 cycles in setup overhead (m_axi
    arbitration, DDR row activation if not cached).  The two-pass approach
    (entry 54) re-reads the same 64 DDR words in a second burst.  The 64
    extra data cycles + 45 setup cycles = 109 extra cycles per pass,
    swamping the 128-cycle theoretical II saving.

    Why block-separated two-burst (entry 58) failed: Same reason — two
    64-word contiguous bursts cost 2 × (45 + 64) = 218 cycles vs one
    128-word burst at II=4 = 256 cycles.  Near break-even before accounting
    for per-call overhead.

    ── Bottleneck 3: INLINE off function call overhead ───────────────────────
    Each load_row_wv_urm call pays m_axi port handshake and function call
    overhead (~45 cycles/call).  With 4 calls per iteration × 2048 iterations
    = 8,192 calls per compute_X1, this adds ~370K cycles.

    Why INLINE (entry 55) barely helped: Only saved ~14K cycles (0.55%).
    The overhead was already priced into the II=4 scheduling — HLS overlaps
    the AXI read with BRAM writes within the II=4 pipeline.  The function
    call overhead is in the AXI burst setup, not the call/return.

    ── Overall time budget (decode, per token, measured) ─────────────────────
    Total: 454 ms/token (2.20 t/s)
      FPGA FFN (16 layers × 19 ms):   304 ms  (67%)
        └ X1/X2 load+MAC per layer:   10.4 ms (II=4 nibble load dominates)
        └ gate:                         0.07 ms
        └ output load+MAC:              6.3 ms (II≈2, 4 group writes)
        └ DATAFLOW overhead:           ~2.5 ms
      CPU attention + norms:          ~125 ms  (28%)
      Driver + output copy:            ~25 ms   (5%)

    ── Amdahl's Law ceiling ─────────────────────────────────────────────────
    The FPGA accelerates FFN (68% of total time).  Non-SwiGLU overhead is
    ~125 ms/token and is fixed.  Even infinite FPGA speed would give:
      max speedup = 1 / (1 - 0.68) = 3.125× over pure CPU
    With CPU decode at 1.15 t/s: ceiling = 3.6 t/s absolute maximum.

    The current 2.20 t/s achieves 61% of the theoretical ceiling.  The
    remaining ~1.4 t/s gap to 3.6 t/s is split between:
      - II=4 nibble load (~40% of gap): cannot fix without hardware change
      - AXI/DDR overhead (~30%): could improve with wider ports or higher clock
      - CPU attention (~30%): outside FPGA scope, requires model/software change

61. II=1 load — exhaustive fix attempts and definitive result.

    The 4-write load fanout is the single performance bottleneck.  Ten distinct
    architectures were synthesized to try to achieve II=1.  All failed.

    | #  | Approach                          | X1/X2     | Why It Failed                               |
    |----|-----------------------------------|-----------|---------------------------------------------|
    | 1  | Explicit II=2 pragma               | 3.12M     | Pipeline buffering > II savings             |
    | 2  | URAM→BRAM swap                     | 2.60M     | Write latency not the issue                 |
    | 3  | Two-pass DDR re-read               | 3.73M     | Second AXI burst setup dominates            |
    | 4  | Two-pass + INLINE                  | 3.73M     | Same AXI overhead, INLINE doesn't fix it    |
    | 5  | INLINE only                        | 2.59M     | Call overhead negligible vs write body      |
    | 6  | 2-slice DDR, interleaved           | 3.13M     | if/else conditional prevented II=1          |
    | 7  | 2-slice DDR, block-separated       | 3.75M     | Two bursts cost more than one at II=4       |
    | 8  | UNROLL output groups               | 1.54M out | Load dominates, not MAC; +102% LUTs         |
    | 9  | Stream-decoupled DATAFLOW          | 2.60M     | Consumer alone can't do 4 writes at II=1    |
    | 10 | Cyclic-4 partition + INLINE        | 2.59M     | Proven bank independence, scheduler ignores |

    Root cause: Vitis HLS 2025.1 scheduler counts memory operations per cycle.
    Each BRAM has 1 write port (ram_1p).  Four writes = 4 port requests in one
    pipeline stage = 4 sequential cycles in the scheduler's model.  The scheduler
    cannot issue 4 operations to 4 single-port memories simultaneously, even when
    banks are proven independent via cyclic partition.

    This is a tool limitation, not a hardware limitation.  The physical BRAMs
    have independent write ports; a hand-crafted RTL design could fan out to
    4 BRAMs at II=1.  But Vitis HLS cannot express this.

    The 2.20 t/s configuration (4 separate BRAM tiles, single DDR burst, INLINE
    off) is the local optimum for this toolchain and device at 250 MHz.
