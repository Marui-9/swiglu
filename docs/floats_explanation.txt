Where floating point remains in swiglu.cpp, and why
(revised 2026-10-03 against swiglu.cpp on branch `rebuild`; the earlier version described
the FP32-activation, 8-accumulator and Q6_K designs)

WHAT IS INTEGER (W4A8)
Both MAC arrays — mac_blocks_wv_k4_urm (X1, X2) and mac_blocks_down_q4k_k2_urm (output) —
run the per-element hot loop in pure integer arithmetic:
   acc_w += act_int8 × nibble(uint4) × sc6(6-bit)     → INT32
   acc_m += act_int8 × mn6(6-bit)                     → INT32
with 4 accumulator slots per block (selected by n & 3). The activations entering the IP and
crossing between stages are INT8: x (host-quantized), X1/X2 (fixed ±10 scale), gate
(per-token max-abs scale).

WHERE FLOAT IS USED (three places)
1. Per-block reduce in both MACs (REDUCE / REDUCE_GRP):
      total += d[b]·Σw − dmin[b]·Σm      (float multiplies, ap_fixed<48,38> accumulate)
      result = total × x_scale  (or × gate_scale)
   This happens once per 256-element block, not per element. d and dmin are fp16 in the
   Q4_K format with arbitrary magnitude (often subnormal), so they cannot be folded into a
   fixed integer range without changing the quantization scheme.
2. compute_gate: dequantize X1/X2 (× 10/127), SiLU via z·sigmoid_lut[idx]·x2, then the
   max-abs scan and requantization of the gate to INT8. SiLU is nonlinear and the gate
   scale is data-dependent. This is the smallest float user (compute_gate: 6,557 LUT in
   swiglu/reports/hls_compile.rpt).
3. mac_quant_wv: X1/X2 result × 12.7, round and clamp to INT8.

THE BOUNDARY WITH llama.cpp IS FP32
Activation tensors in llama.cpp are FP32. The fused op's input x and its output are FP32
tensors; the residual add in lfm2.cpp and the next layer's RMSNorm consume FP32. So the
driver quantizes x to INT8 (max-abs / 127) before the call, and the IP writes FP32 results.
Only the weights stay quantized in DDR.
