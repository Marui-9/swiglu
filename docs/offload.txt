How the offload is wired into llama.cpp
(revised 2026-10-03; line numbers refer to the copies in llama-mods/. The earlier version
also held the K=2 W2/V2 extra-port plan, which never shipped — the IP has five m_axi
ports — and a pre-implementation plan that has since been carried out.)

FILES AND EXECUTION PROCESS OF llama.cpp

 ggml.h     -> no execution logic: tensor structs, the enum of ops, builder prototypes.
 ggml.c     -> graph-building helpers: each builder creates a tensor node with its op and
               inputs wired and returns it.
 ggml-cpu.c -> executor of the CPU backend: thread setup, graph planning, and the
               ggml_compute_forward switch that dispatches per-op kernels. The offload
               logic (udmabuf mmap, register programming, IRQ wait, copy out) lives here.

ggml != llama.cpp: llama.cpp builds the model graph out of ggml ops. The fused op
(ggml_swiglu_fused_hw) is defined in ggml.c and executed in ggml-cpu.c; when it runs, the
backend prepares buffers and registers and starts the FPGA IP. swiglu.cpp is the HLS IP
that computes the FFN block. So: ggml orchestrates and dispatches; swiglu.cpp computes.

End-to-end flow (CPU backend):
1. The model is loaded from GGUF; llama.cpp calls ggml builder functions to construct a
   compute graph of tensors.
2. ggml_graph_compute (ggml-cpu.c:3726) plans the graph and starts the threadpool.
3. Each worker runs ggml_graph_compute_thread (ggml-cpu.c:3451), visiting nodes in
   topological order. For each node, ggml_compute_forward (ggml-cpu.c:2172) — a large
   switch on tensor->op — calls the op's kernel. Threads meet at a barrier after each node.
4. Per-op parallelism is chosen beforehand in ggml_get_n_tasks (ggml-cpu.c:2670). Heavy
   ops (MUL_MAT, GLU) use n_threads and split rows by ith/nth; the fused op uses 1.

THE FUSED OP — WHAT WAS ADDED

1. ggml.h:474   GGML_OP_SWIGLU_FUSED_HW added to enum ggml_op.
   ggml.h:808   declaration:
       GGML_API struct ggml_tensor * ggml_swiglu_fused_hw(struct ggml_context * ctx,
                       struct ggml_tensor * x,      struct ggml_tensor * w_gate,
                       struct ggml_tensor * w_up,   struct ggml_tensor * w_down,
                       int32_t layer_id);

2. ggml.c:957   "SWIGLU_FUSED_HW" added to the GGML_OP_NAME array (for logging).

3. ggml.c:2925  builder. It does NOT call the FPGA; it only creates the node:
       asserts x->ne[0] == w_down->ne[1], w_gate->ne[0] == w_up->ne[0],
               w_gate->ne[1] == w_down->ne[0]
       result = new F32 tensor [w_down->ne[1], x->ne[1], x->ne[2], x->ne[3]]
       result->op = GGML_OP_SWIGLU_FUSED_HW; src[0..3] = x, w_gate, w_up, w_down
       op_params[0] = layer_id   (selects the layer's udmabuf weight slot)

4. ggml-cpu.c:2681  case GGML_OP_SWIGLU_FUSED_HW: n_tasks = 1.
   The kernel is single-threaded; the other CPU threads idle while the FPGA runs.
   ggml-cpu.c:2186  case GGML_OP_SWIGLU_FUSED_HW: reads SWIGLU_DEBUG once, then calls
   ggml_compute_forward_swiglu_fused_hw (ggml-cpu.c:1971). What that function does, step
   by step, is in docs/code_stages.txt.

5. lfm2.cpp:18-41, inside the build_dense_feed_forward lambda — the only call site. The
   insertion is LFM2-specific on purpose, not inside the generic build_ffn(), so no other
   architecture can be routed to the hardware. The fused op is emitted when:
       LLAMA_SWIHW=1 in the environment
       x is F32 with ne[0] == 2048 and ne[1] >= 1     (decode AND prefill)
       ffn_gate is [2048, 8192]; ffn_gate, ffn_up and ffn_down are all Q4_K
   Otherwise the standard build_ffn() CPU path is used. The layer index il is passed as
   layer_id.

BATCH / PREFILL

"Batch" (ggml's second dimension, ne[1]) is the number of tokens processed together: 1 for
decode, >1 for prefill. x is [2048, n_tokens]. The IP has MAX_BATCH = 1, so the driver
loops over the tokens of a ubatch, one IP call each, and asserts if a ubatch has more than
SWG_MAX_TOKENS = 64 tokens. There is no CPU fallback for prefill inside the op.

OVERLAP WITH OTHER CPU WORK
The ggml scheduler is synchronous: a node completes before its dependents start, and there
is no asynchronous node completion. Overlapping the FPGA with the rest of the layer (e.g.
attention of the next token) would need scheduler changes. A lighter option is overlap
inside the kernel (double-buffer x/out across tokens), which only helps prefill.
