\chapter{Experiments and Discussion}
\label{cha:experiments}

\section{Experimental Setup}
\label{sec:setup}

\textbf{Hardware Platform.} Experiments were conducted on the Kria KV260, an embedded
UMA platform whose Processing System (PS) is a quad-core Arm Cortex-A53 running at
1.3\,GHz, with 4\,GB of DDR4 shared between the PS and the programmable logic (PL). The
accelerator runs in the PL at 250\,MHz (the PL0 clock reads 249,999,998\,Hz on the
board). Power is read from the on-module sensors through the AMD \texttt{xmutil}
toolchain.

\textbf{Software Stack.} The inference engine is a modified \texttt{llama.cpp} with the
fused MatMul + SwiGLU operator and its driver (Section~\ref{sec:orchestration}). The
evaluated accelerator is the design described in Chapter~\ref{cha:design}: loop-level
load/compute overlap, INT16 intermediate activations $X_1$/$X_2$ over a fixed $\pm 32$
range, and the \texttt{STABLE} fix of Section~\ref{subsec:stage2}, synthesized and
implemented with Vitis HLS and Vivado 2025.2 (routed with WNS $+0.145$\,ns at a
4.000\,ns clock constraint). An unrelated idle service on the
board was stopped before the measurements. The CPU Only runs were made in a separate
boot in which the accelerator was never loaded, so that the configured fabric does not
add to their power (Section~\ref{sec:results}).

\textbf{Workload.} The evaluation uses the LFM2.5-1.2B language backbone (input
dimension 2048, feed-forward dimension 8192). The accelerator processes one token per
invocation; multi-token prefill is handled by the driver, which issues one IP call per
token. This reflects the single-token synthesis constraint imposed by on-chip memory
limits.

\textbf{Baseline.} The baseline is CPU Only execution of the same model through an
identical inference pipeline. In the accelerated configuration only the MatMul + SwiGLU
block is offloaded to the FPGA, while all remaining operations run on the CPU. Both
configurations use the same modified \texttt{llama.cpp} binary, with the offload
enabled or disabled at runtime through the \texttt{LLAMA\_SWIHW} environment variable
(\texttt{1} for FPGA+CPU, \texttt{0} for CPU Only), without recompilation. Both paths
also load the \emph{same} GGUF file: the Thinking variant quantized as Q4\_K\_M with
every \texttt{ffn\_down} tensor forced to Q4\_K (Section~\ref{subsec:quant}), which
\texttt{llama-bench} reports as 661.76\,MiB. The two paths therefore compute the same
model, and the comparison isolates the effect of the offload.

\section{Evaluation Metrics}
\label{sec:metrics}

\textbf{Throughput} is measured in tokens per second, separately for prefill and decode,
with \texttt{llama-bench} on a fixed workload of 12 prompt tokens and 64 generated
tokens (\texttt{-p 12 -n 64}), repeated over 10 runs. \textbf{Power} is the average of
the ``SOM total power'' reported by \texttt{xmutil platformstats}, sampled about once
per second over the whole benchmark run, so it covers prefill and decode together. From
these, \textbf{performance per watt} (tokens/s/W) is the ratio of throughput to mean
power, and \textbf{energy per decoded token} (J/token) is mean power divided by decode
throughput; both are approximate, because the power average is not split by phase.
\textbf{Peak memory} is the process's VmHWM. \textbf{FPGA time} per token is read from
the driver's per-token instrumentation (\texttt{SWIGLU\_DEBUG=1}).

Because the accelerator quantizes activations, speed alone is not a sufficient metric.
\textbf{Accuracy} is measured against CPU Only on the same GGUF in two ways: perplexity
and the KL divergence of the output token distribution on wikitext-2
(\texttt{llama-perplexity}), and, layer by layer, the cosine similarity between the
accelerator's output and the float CPU feed-forward output for the same input.

\textbf{FPGA resource utilization} (LUT, FF, BRAM, URAM, DSP) is taken from the
post-route Vivado reports.

The FPGA+CPU path is faster than CPU Only at every thread count. The decode speedup is
2.09$\times$ at T1, 1.65$\times$ at T2, 1.38$\times$ at T3 and 1.21$\times$ at T4
(derived). The fastest configuration overall is FPGA+CPU at T3, with 3.53\,t/s against
2.68\,t/s for the best CPU Only configuration (T4), a 1.32$\times$ gain (derived).

\textbf{CPU Only baseline and the PL state.} The board's firmware manager configures a
default design in the PL at every boot, so the fabric is never blank. CPU Only was
therefore measured in a boot in which the accelerator was never loaded. In that boot
the idle module power is 3.27\,W with the default design (100\,MHz) and 3.94\,W once
the accelerator is loaded, with the IP idle at 250\,MHz: the configured accelerator
costs about 0.66\,W even when no call runs (derived). Earlier CPU Only runs, made with
the accelerator loaded or removed through \texttt{xmutil unloadapp} (which does not
blank the PL), gave the same throughput (0.93, 1.76--1.77, 2.54--2.55 and
2.65--2.70\,t/s at T1--T4) but 0.59--0.66\,W more power (derived).

FPGA+CPU draws more power than CPU Only at every thread count: 4.48--4.92\,W against
3.62--4.27\,W, a difference of 0.54--0.86\,W (derived), of the same order as the
0.66\,W that the configured accelerator costs at idle. Its higher throughput more than compensates: the energy per decoded token is
2.31, 1.64, 1.39 and 1.45\,J for FPGA+CPU at T1--T4, against 3.89, 2.24, 1.67 and
1.56\,J for CPU Only, 41\%, 27\%, 16\% and 7\% less (derived). Best against best,
FPGA+CPU at T3 uses 11\% less energy per token than CPU Only at T4, which is also the
most efficient CPU Only configuration (derived).

Peak resident memory (VmHWM) is 694\,MiB for both modes: the GGUF model is memory-mapped
and demand-paged. The FPGA+CPU path additionally holds a 512\,MiB CMA-backed
\texttt{udmabuf} region for the pre-decoded weights and the activation buffers, which
is not counted in RSS. Per-token decode latency (derived as the reciprocal of decode
throughput) is 1075, 565, 391 and 373\,ms for CPU Only at T1--T4, and 515, 342, 283 and
309\,ms for FPGA+CPU.

\textbf{Where the time goes.} The driver's instrumentation reports 129.5--129.6\,ms of
FPGA time per token (16 calls) at every thread count, i.e.\ 8.09\,ms per call
(derived). The whole feed-forward path, including activation quantization, cache
maintenance and result copy, takes 131.1--131.3\,ms per token. At T2 a decoded token
takes 342.5\,ms, of which 131.2\,ms is the offloaded feed-forward path and about
211\,ms is the rest of the graph on the CPU (derived). Subtracting the feed-forward
path from the decode latency at the other thread counts leaves about 384, 152 and
178\,ms of CPU work at T1, T3 and T4 (derived): the CPU part stops improving beyond
three threads and gets slower at four, as the FPGA+CPU drop from 3.53 to 3.24\,t/s
shows; CPU Only gains only from 2.56 to 2.68\,t/s over the same step.

The measured 8.09\,ms per call matches the csynth latency of 8.08\,ms (2,020,192 cycles
at 250\,MHz, derived), and a standalone call outside \texttt{llama.cpp} takes 8.017\,ms
(mean of 49 calls). This was not the case for the first board build of the overlapped
design, which ran at 11.34\,ms per call, 1.41$\times$ its csynth latency, while the
previous, non-overlapped design ran at 1.10. Section~\ref{subsec:stage2} traces that
gap to Stages~2a/2b, whose loop iterations were serialized on the board although csynth
reported them as overlapped, and describes the fix. Against that build, the fix raises
decode throughput by 10--19\% at T1--T4 (1.76, 2.53, 2.98 and 2.73\,t/s before,
derived) and leaves the output unchanged: the perplexity and KL divergence runs of
Section~\ref{sec:accuracy} give identical values, chunk by chunk, on both bitstreams.

\section{Accuracy}
\label{sec:accuracy}

The first board runs of the accelerator measured throughput only. Checking the output
against the CPU path first required fixing the three driver bugs described in
Section~\ref{subsec:driver_bugs}. After that, a per-layer check showed that
the IP matched a C emulation of its own integer datapath (cosine $\geq 0.99946$), so no
interface or layout error remained. However, it matched the float CPU feed-forward
output only at a cosine of 0.9569--0.9944. The cause was the fixed $\pm 10$ INT8 range
of $X_1$/$X_2$: real $|xW^T|$ stays below about 4.3, so most of the 8-bit range was
unused and 801--2,347 of the 8,192 gate products per layer rounded to zero.
Section~\ref{subsec:quant} describes the fix (INT16 over $\pm 32$);
Table~\ref{tab:accuracy} compares the two versions on the board.

\section{Comparison with STM32MP257F-DK}
\label{subsec:stm32comparison}

To contextualize the KV260 results against a different Arm-class edge platform, the
standard LFM2.5-1.2B Q4\_K\_M distribution (8 of 16 down-projection layers at Q6\_K, the
remainder at Q4\_K) was benchmarked on the STM32MP257F-DK, which integrates on chip two
Cortex-A35 cores running at up to 1.5\,GHz. This is not the GGUF used on the KV260, so
the comparison is between platforms running closely related, not identical, models.
Results are reported alongside the KV260 data in Table~\ref{tab:short_results}. Total
board power consumption is derived analytically as the sum of four terms:
\begin{enumerate}[label=(\roman*)]
    \item \textbf{SoC rail power}: datasheet characterization currents~\cite{ds14284} (Tables~22--26, $T_j = 25\,^\circ\text{C}$) multiplied by the PMIC output voltages programmed in the board user manual~\cite{um3385} (\S7.5.3, $V_{\text{DDCPU}} = 0.91\,\text{V}$, $V_{\text{DDCORE}} = 0.82\,\text{V}$); this yields $174\,\text{mW}$ at T1 and $320\,\text{mW}$ at T2,
    \item \textbf{LPDDR4 power}: background-dominated at fewer than 5\% utilization ($\approx 150\,\text{mW}$ independent of thread count),
    \item \textbf{Board peripheral idle power} (GigE PHY, STLINK, Wi-Fi module, eMMC): $\approx 205\,\text{mW}$, constant across T1 and T2,
    \item \textbf{PMIC buck conversion losses} at the operating load, assuming $\eta = 0.86$ for the SoC/DRAM rails and $\eta = 0.88$ for the $3.3\,\text{V}$ peripheral rail.
\end{enumerate}
Summing all terms gives a total board input power of $0.62\,\text{W}$ (T1) and
$0.80\,\text{W}$ (T2).

\section{Discussion}
\label{sec:discussion}

With load/compute overlap and the corrected datapath, the FPGA+CPU path is preferable
to CPU Only at every thread count, in throughput and in efficiency. Decode t/s/W
improves by 69\%, 37\%, 20\% and 7\% at T1--T4, and prefill t/s/W by 102\%, 53\%, 26\%
and 14\% (derived). The gain shrinks as threads are added because the offloaded part is
fixed at about 131\,ms per token, while the CPU's share of the work keeps getting faster
up to T3: at T1 the FPGA replaces the slowest part of a single-threaded token, while at
T4 the decode gain is down to 1.21$\times$. The efficiency gain is smaller than the
speedup at every thread count because FPGA+CPU draws 0.54--0.86\,W more than CPU Only
(derived), of the same order as the 0.66\,W idle cost of the configured accelerator,
which is paid also during the 54\% of a T3 token in which the IP is idle (derived from
129.5 of 283.3\,ms).
The FPGA+CPU path also slows from T3 to T4 (3.53 to 3.24\,t/s) while its FPGA time is
unchanged, so the loss is on the CPU side; the cause has not been measured.

The results confirm that offloading the MatMul + SwiGLU feed-forward block is beneficial
because it targets the runtime-dominant kernel, consistently with prior transformer
accelerators that focus on FFN/MLP and attention substructures as the most advantageous
hardware targets~\cite{lu2020hw-mha}. They also show where the remaining time lies:
at T2, the 211\,ms of non-offloaded CPU work is now 1.6 times the 131\,ms feed-forward
path (derived), and the two do not overlap, because the driver blocks the graph while the IP runs.

Comparing the KV260 against the STM32MP257F-DK isolates the effect of the wider
Cortex-A53 pipeline and FPGA fabric from the Cortex-A35 baseline. The A35 achieves
1.28\,t/s decode at T2, versus 1.77\,t/s for the KV260 A53 at T2 (CPU Only) and
\textbf{2.92}\,t/s for the KV260 FPGA+CPU path, a \textbf{2.28$\times$} decode speedup
at matched thread count (derived), at the cost of a more complex integration and about
\textbf{4.0}\,W of additional board power (4.78\,W versus an estimated 0.80\,W). The
STM32 remains 2.62$\times$ more efficient (1.60\,t/s/W decode versus 0.611\,t/s/W,
derived), so the accelerator is justified by its latency margin rather than by energy:
it brings the language model to 342\,ms per token with two threads, while the A35 needs
781\,ms.

Section~\ref{sec:research_question} defined a per-token generation latency target of
200--500\,ms for the language model component. Of the eight KV260 configurations, five
enter this range: T3 and T4 CPU Only (391 and 373\,ms) and T2, T3 and T4 FPGA+CPU (342,
283 and 309\,ms); FPGA+CPU at T1 misses it narrowly (515\,ms). No configuration reaches the 200\,ms instantaneous threshold. The
FPGA+CPU path reaches sub-500\,ms decode with two active CPU threads, whereas CPU Only
needs three. This thread advantage matters in practice: a full conversational pipeline
must concurrently run ASR and TTS stages that compete for the same A53 cores, so
reducing the language model's thread demand directly widens the scheduling budget for
the surrounding stages. The fastest configuration, FPGA+CPU at T3, still uses 283\,ms
of the 500\,ms budget for the language model alone, leaving little headroom for ASR and
TTS; meeting the 0.5\,s aggregate target in a streaming pipeline will require either a
faster platform or accepting the ``immediate'' perceptual range (0.5--1\,s) defined in
Section~\ref{sec:research_question}.

The contrast highlights that the practical value of the FPGA offload scales with the gap
between the host CPU and the accelerator: on a weaker host the absolute gain is larger,
while on a stronger host (more A53 threads) the CPU closes the gap.
Table~\ref{tab:kv260_comparison} places this design within the space of published KV260
accelerators; unlike compute-intensive matrix-multiply designs that saturate DSP slices,
the MatMul + SwiGLU kernel is bounded by the DDR port bandwidth in Stages~2a/2b and by
the LUT and routing capacity that caps the Stage~5 MAC array (86.7\% LUT, 19\% DSP).

Results reported using larger FPGA platforms suggest that greater memory bandwidth and
fabric capacity help kernel-level gains and end-to-end speedup~\cite{FTRANS}. Direct
comparison with the 6.6k-parameter Tiny Transformer on the same platform highlights the
resource intensity of conversational architectures. While the Tiny Transformer maps its
entire end-to-end pipeline at low resource utilization across all fabric categories
(Table~\ref{tab:kv260_comparison}), accelerating just the feed-forward MatMul + SwiGLU
block of the 1.2B-parameter LFM2.5 model nearly saturates the same device at 86.7\% LUT
utilization at 250\,MHz. Critically, the Tiny Transformer's small parameter count is not
merely a resource advantage~\cite{11310944tin}: by fitting the entire pipeline on chip,
it eliminates off-chip weight fetching entirely, allowing execution to remain
compute-bound and sustain near-peak arithmetic throughput, a regime that larger models
cannot achieve on the same device. The Self-Attention
accelerator~\cite{li2025fpgabasedhardware} highlights differing architectural trade-offs:
its two-level tiling strategy keeps both matrix operands within on-chip BRAM across the
Q, K, and V projections, allowing a fully-unrolled $32\times32$ MAC array to sustain 1024
concurrent INT8 operations per cycle without off-chip bandwidth pressure, reaching 91\%
effective utilization of peak throughput. This is achievable because the DistilBERT-scale
projection matrices fit within the on-chip tiling footprint. The LFM2.5 SwiGLU weights,
by contrast, occupy $3 \times 10{,}485{,}760$\,B $\approx 31.5$\,MB per layer in the
pre-decoded device layout, far beyond the ZU5EV's combined on-chip capacity of roughly
3.4\,MB (block, ultra, and distributed RAM combined), which makes DDR streaming
unavoidable. A comparable BRAM-banked matrix multiplication study~\cite{11311069}
reports similar severe PS-side bottlenecks, reaching only 59\% of its peak throughput.
In the present design, the csynth schedule keeps the Stage~2 weight loads at about 92\%
of the 128-bit port bandwidth and the Stage~5 MAC array about 82\% busy
(Sections~\ref{subsec:stage2} and~\ref{subsec:stage5}). The board matches this
schedule: the DDR controller's performance monitor measures the gate-weight port at
3.68\,GB/s during Stages~2a/2b, and the whole call reaches 6.22\,G\,MAC/s against the
6.23 that the csynth latency implies (derived).

The 19\% DSP usage is a consequence of that bandwidth limit, not of an operand-width
mismatch. In Stages~2a and 2b each of the 32 MAC lanes binds one DSP48E2, which
multiplies the 12-bit nibble$\times$activation product by the 8-bit sub-block scale; the
narrow $4\times8$-bit nibble product and the minimum-term products map to LUTs. Stages~2a
and 2b use 84 DSPs each (32 in the MAC array), Stage~5 uses 48 (32 in its MAC array), and
the gate uses 22 (csynth); the other DSPs serve the floating-point block reduce. More lanes would not help Stages~2a/2b, whose loads already use most of
the port bandwidth, and Stage~5 was deliberately narrowed to 16 lanes to fund the
overlap buffers (Section~\ref{subsec:stage5}). The worst timing path of the routed design
runs through one of the down-projection MAC DSPs.

Extending hardware acceleration beyond the MatMul + SwiGLU block to the Final Linear
Projection and Gated Short Convolution yields diminishing returns, as they account for
only 10.96\% and 10.44\% of total execution time, respectively. Furthermore, simultaneous
acceleration is infeasible on the KV260, as the MatMul + SwiGLU kernel alone uses
86.7\% of the LUTs. To characterize the attainable design space, many architectural
variants were synthesized and evaluated during development, varying the nibble storage
width, the BRAM banking strategy, the AXI burst organization, the use of function
inlining and stream decoupling, and finally the overlap of loads with computation.

Four findings stand out. First, \emph{burst organization matters more than burst
parallelism}. Each DDR burst pays a setup overhead on the HP-port interconnect before
data flows, so one contiguous 320-word burst per four-row group outperformed every
split-burst variant. Its first implementation failed placement at 138K LUTs; a later
version fitted, took Stages~2a/2b from 2.60M to 1.54M cycles, and the current design
keeps it.

Second, \emph{the scheduling limits that once bounded Stage~5 were removable}. An early
down-projection loader had to write each 128-bit word into four single-port buffers in
the same cycle, and Vitis HLS would not schedule it at $II=1$, whatever the storage type
or partitioning. The shipped loader does not have this structure: its nibble loop runs at
$II=1$ (257 cycles for 256 words) in both the previous and the current design. What did
remain was a load-bound stage, in which the MAC array waited for each row. Loop-level
overlap removed that: with the load running concurrently with the MAC, an iteration
costs the longer of the two, and both projection stages became MAC-bound. Stage~5 had
to drop from four to two rows per iteration for this to pay off, because a four-row load
(1,908 cycles) would still exceed the MAC (1,243 cycles).

Third, \emph{routing density remains a hard ceiling}. A fully-unrolled output MAC array,
fed by wide-BRAM reads, gate-cache lookups, and sub-block-scale accesses, exceeds the
device's routable interconnect at 250\,MHz: the wide-BRAM output variant reaches its
target cycle count in synthesis but leaves more than 74,000 unresolved routing-node
overlaps in implementation. Two HLS idioms also inflated the csynth LUT estimate by
tens of thousands before they were caught (Table~\ref{tab:design_space}), which matters on a
device that is already 87\% full. A migration to the ZU7EV (the next device in the same
Zynq UltraScale+ family, with approximately 230\,K LUTs on the same processor--fabric
interface) would be expected to provide the headroom to route a wider output array; it
was not tried.

Fourth, \emph{a csynth interval is a schedule, not a measurement}. The loop-level overlap
of Stages~2a/2b was reported at 348 cycles per iteration while the hardware ran at 745,
and the 1.41$\times$ board/csynth ratio it produced was first attributed to DDR
contention. Only a trace of the DDR traffic per stage on the board, and a C/RTL
co-simulation with dataflow profiling, showed that the iterations were serialized
(Section~\ref{subsec:stage2}). With the fix, a call takes 8.09\,ms on the board against
a csynth latency of 8.08\,ms.
