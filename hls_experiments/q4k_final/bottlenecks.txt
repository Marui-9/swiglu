Bottlenecks and Limitations — q4k_final Architecture
================================================================================
Written 2026-05-29; corrected 2026-10-03 (branch rebuild).
Sources: q4k_final/csynth.rpt (Vitis 2025.1, 2026-05-28), utilization.txt and timing.txt
(routed design), scripts/results/latest_benchmarks/*.log, thesis/latest_findings.md (the
measured T2 per-token split), swiglu/reports/hls_compile.rpt (rebuild csynth).
Board clock 250 MHz (4 ns). The csynth target is 3.33 ns, so csynth slack is not a 250 MHz
figure.


CORRECTION (2026-10-03)
--------------------------------------------------------------------------------
The first version of this file assumed each FPGA call costs the 6.49 ms DATAFLOW interval.
It then put the rest of the measured 14 ms/call down to ~7.5 ms of interrupt delivery.
That was wrong:

  - Decode makes one call per layer per token, so every call pays the full pipeline
    latency: 3,175,430 cy = 12.70 ms at 250 MHz (csynth).
  - The board measures 14.0 ms/call (224 ms/token at T2, the SWIGLU_DEBUG `fpga` figure).
    Only ~1.3 ms of that is above the csynth latency, and the interrupt wake is inside
    that 1.3 ms.
  - The polling driver (changelog entries 67-68) confirmed it. Decode t/s:

        Threads   interrupt (*_q4k.log)   polling (*_pollfix.log)
        T1        1.63                    1.74
        T2        2.21                    2.22
        T3        2.05                    2.10

    This file had predicted ~3.4 t/s at T2.

Every projection built on the 7.5 ms figure has been removed: the old interrupt-latency
section, the testblock Amdahl section, the polling fix, and the t/s estimates for the merged
load and 300 MHz.

================================================================================
1.  PER-CALL LATENCY IS THE SUM OF THE STAGES
================================================================================

    Stage               Cycles       @ 250 MHz
    load_x_local            202
    compute_X1 ∥ X2   1,536,001       6.14 ms
    compute_gate         16,622       0.07 ms
    compute_output    1,622,602       6.49 ms
    ──────────────────────────────────────────
    Latency           3,175,430      12.70 ms   (202 + 1,536,001 + 16,622 + 1,622,602
                                                 = 3,175,427)
    Interval          1,622,603       6.49 ms

compute_output sets the DATAFLOW interval. The interval only matters when calls stream back
to back. Decode cannot do that, because each layer's FFN input depends on the previous
layer's output through CPU-side ops.

So both X1/X2 and the output stage count in full toward the time per call. The first
version said that speeding up X1/X2 alone "yields zero throughput improvement"; for decode
that was wrong. The rebuild cuts both stages.

Board vs csynth: 14.0 / 12.70 ≈ 1.10 (derived).


================================================================================
2.  SEQUENTIAL ROW LOADS IN COMPUTE_OUTPUT
================================================================================

q4k_final, per DOWN_Q4K iteration (512 iterations, K=4 rows):
    load_row_down_urm × 4 :  4 × 477 = 1,908 cy   (60.3%)
    mac_blocks_down       :            1,243 cy   (39.3%)
    overhead              :               14 cy
    total                 :            3,165 cy   → 1,620,480 cy for DOWN_Q4K

Each call opens its own burst for one 320-word row. The original proposal was to merge the
4 rows into one 1,280-word burst, as load_4rows_wv_urm does for W/V. The obstacle: each
nibble word fans out to 4 group tiles per row, so 16 tile writes per word for 4 rows.

What the rebuild did instead (d4942c8):
  - Loop-body DATAFLOW with K=2 rows per iteration.
  - Load 960 cy vs MAC 1,248 cy → 1,249 cy per iteration, MAC-bound.
  - compute_output = 1,282,062 cy (5.13 ms) (hls_compile.rpt).
  - The load is now hidden; merging it would no longer save time.


================================================================================
3.  DOWN_GROUPS RUN SEQUENTIALLY
================================================================================

mac_blocks_down_q4k_k4_urm processes the 32 blocks as 4 sequential groups of 8:
4 × 308 = 1,232 of its 1,243 cycles.

Per group (csynth): MAC_GRP 64 DSP / 20,736 LUT; REDUCE_GRP 20 DSP / 8,382 LUT.

Fully unrolling DOWN_GROUPS would add 3 × (20,736 + 8,382) ≈ 87K estimated LUT. That takes
the estimate from 148K to ~235K. Even scaled by q4k_final's routed/estimate ratio (0.69,
derived) that is ~161K, above the 117,120 available. Infeasible on ZU5EV.

DSP is not the limit: the routed design uses 254 of 1,248. The first version said "Vivado
adds DSPs (286 → 338)". That was wrong: 338 was another design's count, and q4k_final
routed at 254, below its 286 estimate.

The rebuild went the other way: it halved the lanes (K=2) and is MAC-bound at 1,248 cy per
iteration.


================================================================================
4.  NO LOAD/MAC OVERLAP IN COMPUTE_X1/X2   (fixed in the rebuild)
================================================================================

q4k_final, per COMPUTE_X1 iteration (2048 iterations, 4 rows each):
    load_4rows_wv_urm    : 401 cy
    mac_blocks_wv_k4_urm : 315 cy
    overhead             :  34 cy
    total                : 750 cy   → 1,536,000 cy

Load and MAC ran back to back. The proposed ping-pong buffer was implemented in the rebuild
(4493272):
  - Loop-body DATAFLOW with the tile and header arrays declared inside the loop body; HLS
    generates the PIPO buffers.
  - Load interval 320 vs mac_quant_wv (MAC + INT8 quantize) 347 → 348 cy per iteration.
  - compute_X1 = 713,107 cy (2.85 ms) (hls_compile.rpt).
  - Estimated BRAM_18K went from 110 to 150.

Corrections to the first version:
  - It said HLS DATAFLOW cannot double-buffer inside a process. Loop-body DATAFLOW does
    exactly that.
  - It quoted "current total BRAM_18K: 86.5". That was another design's routed count of
    BRAM36 tiles. q4k_final routed at 46.5 BRAM36.


================================================================================
5.  T4 DECODE REGRESSION (HOST SIDE)
================================================================================

    T4 FPGA+CPU decode: 1.46 t/s   (685 ms/token)
    T3 FPGA+CPU decode: 2.05 t/s
    T4 CPU-only decode: 2.31 t/s

FPGA time per token is fixed at ~224 ms. The rest of the T4 token is therefore ~460 ms,
against ~227 ms at T2 (derived).

The cause has not been measured. The working hypothesis (thesis/latest_findings.md) is
scheduler contention at 4 threads. Thread 0 blocks for each FPGA call while the other
threads park at the ggml barrier.

The first version blamed UIO interrupt preemption specifically. Polling barely moved T1-T3,
and there is no T4 polling run, so that is unconfirmed.

Untested fixes:
  - pin the offload thread (sched_setaffinity);
  - set IRQ affinity;
  - stop parking every thread at the barrier during the FPGA wait.


================================================================================
6.  NON-FFN CPU TIME (AMDAHL)
================================================================================

Measured T2 token (thesis/latest_findings.md):
    224 ms FPGA + 227 ms non-FFN CPU + 1.3 ms handoff ≈ 452 ms → 2.21 t/s

Derived limits at T2:
    FPGA time → 0:          1000 / (227 + 1.3)       ≈ 4.4 t/s
    FPGA time halved:       1000 / (112 + 227 + 1.3) ≈ 2.9 t/s

About the old "125 ms floor":
  - It came from the testblock: a pass-through IP at 8.02 t/s decode (changelog entry 11).
  - That run was an older build. Its thread count was not recorded.
  - Its same-session CPU-only run gave 2.89 t/s, faster than any CPU run in
    latest_benchmarks (best 2.36 t/s at T3).
  - So do not combine 125 ms with the current measurements. Use 227 ms for T2.


================================================================================
7.  LUT HEADROOM
================================================================================

Routed: 101,639 / 117,120 LUT = 86.78% (utilization.txt). Headroom 15,481 LUT.

The HLS estimate was 148,042 (126%). Routed/estimate = 0.69 (derived); that ratio is not a
promise for other designs.

Per-module estimates (csynth):
    compute_X1      46,238
    compute_X2      46,238
    compute_gate     6,548
    compute_output  42,838
      of which load_row_down_urm 7,207

The rebuild is estimated at 145,719 LUT. Whether it fits will only be known from Vivado.


================================================================================
8.  TIMING MARGIN AT 250 MHZ
================================================================================

csynth estimates −0.81 ns slack on the MAC/REDUCE modules. That is against the 3.33 ns
target, not 250 MHz.

Routed at 250 MHz (timing.txt):
    WNS −0.023 ns   TNS −1.699 ns   150 failing setup endpoints
    WHS +0.010 ns   0 failing hold endpoints

All failing paths are DSP→DSP inside compute_output: DSP_OUTPUT_INST/CLK →
ALU_OUT[10..19], 1.692 ns logic + 2.240 ns net.

The design was exported with setup failing by 23 ps and ran correctly on the board
(changelog, first entry 62). The first version of this file recorded that hold was closed
with phys_opt_design -hold_fix.

Plan for the rebuild (CLAUDE.md): set_clock_uncertainty -setup 0.300 on the PL clock in
Vivado to buy real margin. Do not relax the HLS clock.


================================================================================
9.  LOAD_HDR_DOWN AT II=2 (MINOR)
================================================================================

LOAD_HDR_DOWN needs two 128-bit reads per block header (32 B), so it runs at II=2: 70 cy for
32 blocks, against ~36 cy at II=1.

In q4k_final that wasted 34 cy × 4 calls × 512 iterations = 69,632 cy (~4% of
compute_output).

In the rebuild it is still II=2 (71 cy), but the whole load is hidden behind the MAC, so it
no longer costs time.
