Power and throughput profiling on the KV260
(revised 2026-10-03; rebuild_s2fix results added 2026-10-24. The earlier version held a
copied Smart Camera tutorial, a 2020.2-image sample output and an open "TO QUANTIFY" list
with numbers from the testblock era; the questions it raised have since been measured, see
below.)

READING POWER
   xmutil xlnx_platformstats -p
The "Power Utilization" section gives SOM total power / current / voltage. These are
whole-SOM numbers (PS + PL + DDR), so the accelerator's power is only visible as the
difference between a CPU-only run and an FPGA+CPU run of the same workload. Readings also
drift with ambient temperature; compare runs made back to back.
A full sample of the command's output is in scripts/util/platformstats_sample.txt.

MEASURING A RUN
scripts/profiling/run_profile_cpu.sh and run_profile_accel.sh (usage: <threads> [repeat];
the accel script runs llama-bench under sudo and is itself started with sudo) run
   llama-bench -m $MODEL -p 12 -n 64 -t <threads> -r <repeat>
with a 1 Hz power/temperature logger and an RSS logger (VmRSS and VmHWM) in the background,
and append an "Avg power" summary to $LOG_DIR/{cpu,accel}_t<threads>_<timestamp>.log.
MODEL defaults to ~/LFM2.5-1.2B-Thinking-Q4_K_M-allQ4Kffn.gguf for both scripts, so both
paths run the same GGUF; LOG_DIR defaults to /tmp. The accel script sets LLAMA_SWIHW=1
SWIGLU_DEBUG=1; the CPU script runs without the offload.

MEASURED RESULTS (rebuild_s2fix bitstream, 250 MHz, 2026-10-24; current)
Logs: scripts/results/rebuild_s2fix_final_20261024/bench/ (FPGA+CPU T1-T4, CPU-only T3/T4), r=10.
CPU-only T1/T2 are from the same scripts on 2026-10-23
(scripts/results/rebuild_x16_20261023/bench/); the T3/T4 control matched that day to
within 0.04 t/s. Same GGUF on both paths (allQ4Kffn, 661.76 MiB in llama-bench).

   threads   FPGA+CPU decode   avg power   CPU-only decode   avg power
   T1        1.94 t/s          4.48 W      0.93 t/s          4.28 W
   T2        2.92 t/s          4.78 W      1.76 t/s          4.60 W
   T3        3.53 t/s          4.92 W      2.54 t/s          4.86 W
   T4        3.24 t/s          4.71 W      2.69 t/s          4.76 W

Derived (scripts/results/rebuild_s2fix_final_20261024/README.md): energy per decoded token
2.31 / 1.64 / 1.39 / 1.45 J (FPGA+CPU) vs 4.60 / 2.61 / 1.91 / 1.77 J (CPU-only); best vs
best 3.53 vs 2.69 t/s (1.31×) at 1.39 vs 1.77 J/token. These t/s come with mean KLD 0.030154
and PPL ratio 1.034376 vs the CPU path (wikitext-2, 6 × 256, T2).

The FPGA+CPU power is lower than q4k_final's ~5.1 W below. Those runs were on another day
and another bitstream, so the difference is not attributed to anything in particular.

MEASURED RESULTS (q4k_final bitstream, 250 MHz, interrupt build; superseded)
Logs: scripts/results/latest_benchmarks/{accel,cpu}_t<N>_q4k.log, r=10.

   threads   FPGA+CPU decode   avg power   CPU-only decode   avg power
   T1        1.63 t/s          5.10 W      0.88 t/s          3.96 W
   T2        2.21 t/s          5.15 W      1.66 t/s          4.25 W
   T3        2.05 t/s          5.14 W      2.36 t/s          4.41 W
   T4        1.46 t/s          5.13 W      2.31 t/s          4.28 W

The polling build (accel_t<N>_pollfix.log) is barely faster (T2 2.22 t/s) but draws more
(T2 5.85 W), because the CPU busy-waits instead of sleeping on the interrupt.

Caveat: the two columns did not run the same GGUF. llama-bench reports 628.25 MiB for the
accel runs (the all-Q4_K requantization) and 694.76 MiB for the CPU runs (the stock
Q4_K_M, which keeps Q6_K tensors), although both scripts named the same model path. The
stock Q4_K_M file on hand is corrupt from blk.4 on (CLAUDE.md, Model), so those CPU runs
very likely ran a corrupt copy: their timing is valid, their output was never checked.
cpu_t<N>_q0.log are CPU runs of a Q4_0 model (661.25 MiB).

Older files in scripts/results/ (power_results_T*.txt, power_summary_T1_T4.csv and its
plots, the top-level accel_/cpu_ logs, old/) are from earlier bitstreams and earlier CPU
builds (including the noNEON runs); they do not describe q4k_final.

WHERE THE TIME GOES (T2)
Measured with SWIGLU_DEBUG=1 (per-token [SWG] lines; docs/output.txt is a q4k_final sample).
rebuild_s2fix, 342.5 ms/token (derived: 1000 / 2.92; rebuild_s2fix_final_20261024/README.md):
   FPGA compute, 16 layers            129.5 ms  (8.09 ms/layer)
   host<->device handoff              ~1.65 ms  (quantize x, cache syncs, copy-out, registers)
   rest of the graph on the CPU       211.3 ms  (attention, conv, norms, lm_head, sampling)
q4k_final, 452 ms/token (latest_findings.md): ~224 ms FPGA (14.0 ms/layer),
~227 ms non-FFN CPU, ~1.3 ms handoff.
While the FPGA runs, the calling thread sleeps in the UIO read() and the other thread idles
at the ggml barrier (the fused op has n_tasks = 1).
