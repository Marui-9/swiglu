INT8 X1/X2 intermediate caches — design record
(written 2026-04-02 as a step-by-step patch plan. That plan is implemented in swiglu.cpp,
and its line-number instructions no longer apply; condensed 2026-10-03 to the rationale
and the open question.)

WHAT CHANGED
X1_cache and X2_cache went from float[1][8192] (32 KB each, one URAM each) to
int8_t[1][8192] (8 KB each, BRAM ram_2p). gate_cache was already INT8 in URAM. This freed
2 URAM blocks and removed the wide URAM read ports that fed compute_gate. The IP's
external interface did not change (INT8 x in, FP32 out, same registers).

In the current code:
  X12_SCALE_RANGE = 10.0f
  X12_INV_SCALE   = 127/10 = 12.7     mac_quant_wv: round-half-away, clamp to [-128, 127]
  X12_QUANT_SCALE = 10/127 ≈ 0.0787   compute_gate: dequantize before SiLU

WHY A FIXED SCALE (unlike the gate's dynamic two-pass scale)
A dynamic per-token scale for X1/X2 would need either 8192 floats of buffering per cache
(which cancels the memory saving) or a second pass over W/V from DDR (2 × 10 MB more
traffic per call). A fixed scale is single-pass with no extra traffic.

Quantization step: 10/127 ≈ 0.079, so ±0.039 rounding error — 0.4% relative at |X1| = 10,
4% at |X1| = 1.

OPEN QUESTION — THE ±10 BOUND IS UNVERIFIED
The original plan stated that LFM2 X1/X2 activations satisfy |X1|, |X2| ≤ 10 "from the
model's activation statistics", but no statistics, script or log backing this exists in
the repository. Values beyond ±10 are silently clamped to ±127, which would distort SiLU
for large pre-activations. Before relying on this scale in the rebuild, measure the real
per-layer max |W_gate·x| and |W_up·x| on CPU (e.g. a ggml callback over a few hundred
tokens) and choose the range from that data.
