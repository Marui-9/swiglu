Bottleneck Analysis — K_WV=12 Parallel REDUCE, MAX_BATCH=4, actual_tokens
=============================================================================
Date: 2026-05-23  |  Based on: csynth.rpt (May 23) + Vivado implementation
HLS: 78,730 LUTs (67%), 158 DSP (12%), 266 BRAM (92%), 127K FF (54%), 32 URAM (50%)
Vivado: 101,182 LUTs (86.4%), routes and closes timing at 250 MHz
Decode: 3.99M cycles, 2.63 t/s.  Prefill (B=4): 2.59M/token, 3.44 t/s.


1. DDR Load Bandwidth — 43% of Decode Cycles, Saturated
---------------------------------------------------------
Weight load phases consume 1.72M of 3.99M decode cycles. Both WV and output
ports operate at 128 bits/cycle (97.5% of 4 GB/s peak). ZU5EV HP ports are
128-bit max — no wider AXI possible.

  WV load:   1,110 cyc/iter × 683 iter = 0.76M (19% of decode total)
  Out load:  470 cyc/MG × 8 MG × 256 iter = 0.96M (24% of decode total)
  Combined:  1.72M (43%)

At actual_tokens=4, DDR load amortized N-fold: per-token DDR cost drops to
0.43M (17% of per-token cycles). But single-token decode can't benefit —
the load-then-compute pattern means every decode call pays the full DDR cost.

Structural fix: overlapping weight pre-load with MAC compute (load row N+1
while MAC row N). Requires double-buffered nib_r storage. Attempted via HLS
DATAFLOW — works architecturally (3.13M cycle proof-of-concept) but HLS
duplicates hardware inside DATAFLOW (2× load, 2× MAC) → 149K LUTs. Not viable
on ZU5EV without RTL-level control of the load/MAC pipeline.


2. LUT Budget — 86.4%, the Binding Resource Constraint
--------------------------------------------------------
Vivado LUTs at 101K of 117K. Headroom: 15.8K (13.6%). Every K_WV increment
adds ~7K HLS LUTs per instance (~18K Vivado) from wider nibble-read muxes
and DSP routing. K_WV=14 and K_WV=16 both exceed 117K at 134K and 135K
respectively — MAC_ALL achieves II=1 at both widths but Vivado routing
inflates LUTs super-linearly.

DSP (6.9%), URAM (12.5%), and LUTRAM (7.8%) have massive headroom but cannot
substitute for routing LUTs — the load-function AXI address computation and
12-way LOAD_NIB demux dominate LUT usage in ways DSP/URAM can't address.

Attempted mitigations:
  - Time-mux REDUCE: reduced REDUCE_GRP LUTs 56% but added DATAFLOW control
    sets → Vivado CLB packing failure (2,260 > 2,188 threshold). Reverted.
  - CPU pre-converted d: moved float→fixed conversion to software → saved
    ~29K Vivado LUTs. Worked — enabled K_WV=12 to fit at same LUT budget
    as K_WV=10 baseline.
  - URAM nib_r: would free 48 BRAM but read latency (3-4 cyc) adds 3 cycles
    to MAC_ALL (260→263). Minimal. But double-buffered URAM at K_WV=12
    requires 48 of 64 blocks (75%) — double-buffering for load/MAC overlap
    would need 96 blocks. ZU5EV has only 64. Not viable.


3. K_WV Scaling Ceiling — II=1 Holds, LUTs Don't
--------------------------------------------------
K_WV=12: MAC_ALL II=1 at 12 chains, 260 cycles. Fits Vivado (101K LUTs).
K_WV=14: MAC_ALL II=1 at 14 chains (confirmed HLS). Vivado: 134K LUTs (114%).
K_WV=16: MAC_ALL II=1 at 16 chains (confirmed HLS). Vivado: 135K LUTs (115%).

The ZU5EV fabric sustains II=1 with up to 16 parallel BRAM reads + 16 DSP
routes per cycle at 250 MHz (proven in HLS). But the Vivado router inflates
LUTs to meet timing at these densities — super-linear growth beyond 12 chains.
Physical floorplanning (Pblocks) might constrain the placer and reduce inflation,
but has not been attempted.

K_WV=12 is the practical ZU5EV ceiling with the current HLS flow.


4. Output Path — 39% of Decode, DDR-Dominated
-----------------------------------------------
compute_output consumes 1.54M cycles (39% of decode). Within it, DDR load
dominates at 63% (3,760 of 5,985 per-iteration cycles). MAC_MG at 37% is
well-provisioned (64 parallel DSPs, II=1).

K_DOWN=16 attempted: doubled parallelism, halved iterations (256→128).
Failed Vivado at 130.8K LUTs — REDUCE_MG 16 parallel DSP routes inflate
LUTs super-linearly (same mechanism as K_WV scaling).

Output time-mux REDUCE: reduced REDUCE_MG from 8→1 DSP but added 295K cycles
because REDUCE(64) > MAC_MG(35) — overlap can't hide REDUCE time. Reverted.

The output path is the second-largest cycle consumer but has proven harder
to improve than the WV path — tighter cycle budget per operation leaves less
room for overlap-based optimization.


5. Token Pipelining — HLS DATAFLOW Limitation
-----------------------------------------------
Overlapping token N's output with token N+1's compute would reduce effective
per-token latency from 3.99M to max(2.43M, 1.54M) = 2.43M (39% reduction).
Double-buffered intermediate storage (X1/X2/gate caches) fits within BRAM
budget. But HLS DATAFLOW requires each process to run to completion before
the next can consume its output — no mechanism for "slot 0 is ready, start
consuming it while slot 1 is produced." Full pipeline duplication is the only
HLS-expressible path (2× hardware → 218K Vivado → doesn't fit).


6. 300 MHz Clock — Control Set Density
----------------------------------------
HLS synthesized successfully at 3.33 ns. Vivado failed CLB packing: 2,240
control sets vs 2,188 threshold. Each DATAFLOW region, pipeline stage, and
reset domain creates a unique control set. At 250 MHz, the design sits just
under the CLB packing threshold; at 300 MHz, Vivado inserts additional
pipeline registers for timing, inflating control set count past the limit.

config_rtl -reset state was attempted but did not reduce control sets
sufficiently. Clock scaling is blocked by control set density, not
absolute FF/LUT count or timing slack.


7. Amdahl's Law — CPU Overhead Limits Returns
-----------------------------------------------
CPU overhead (attention, layer norms, embedding, sampling, driver) is ~125 ms
per token — fixed regardless of FPGA speed.

  Decode at 2.63 t/s:   255 ms FPGA + 125 ms CPU = 380 ms total
  Prefill at 3.44 t/s:  166 ms FPGA + 125 ms CPU = 291 ms total (per-token avg)
  Theoretical max:        0 ms FPGA + 125 ms CPU = 8.0 t/s

Each incremental FPGA improvement yields diminishing throughput returns.
Going from 2.63→3.0 t/s requires −740K cycles (−18.6%). Going from 3.0→3.5
requires another −480K. The fixed CPU component makes each step harder.

CPU overhead could be reduced by: driver interrupt batching, layer norm
offload to FPGA (32 reductions/token, ~5-10 ms), or speculative decode to
amortize CPU attention across multiple FPGA-generated tokens. None implemented.


8. Resource Mismatch — Abundance Can't Substitute for Scarcity
---------------------------------------------------------------
DSP (6.9%), URAM (12.5%), and LUTRAM (7.8%) have massive headroom but are
structurally mismatched to the design's actual bottleneck: LUT-based routing.
DSPs compute but can't route. URAM stores but can't mux. The nibble
extraction muxes, AXI address computation, and DATAFLOW pipeline registers
consume LUTs in ways no other resource can substitute.

The only effective LUT reductions found were: CPU pre-conversion (eliminates
float→fixed converters, −29K Vivado) and narrow fxd_scale_t (eliminates
DSP cascades, −12K Vivado). Both are already applied.


Summary — Bottleneck Ranking
-----------------------------
  Rank  Bottleneck                    Impact             Fixable?
  ─────────────────────────────────────────────────────────────────────
  1.    DDR load bandwidth            43% of cycles      Partial (batching helps prefill)
  2.    LUT budget                    86.4% used         No (K_WV ceiling reached)
  3.    Output path DDR load          24% of cycles      No (ports saturated)
  4.    Token pipelining              39% possible gain  No (HLS DATAFLOW limitation)
  5.    Amdahl CPU overhead           125 ms/token       Partial (driver optimization)
  6.    K_WV scaling                  II=1 holds         No (Vivado LUT inflation >12)
  7.    300 MHz clock                 10% possible       No (control set density)
  8.    Load/MAC overlap              33% possible       No (DATAFLOW hardware dup.)

The design is at the ZU5EV Pareto frontier for Q4_0 HLS SwiGLU acceleration.
Further gains require either a larger device (ZU7EV: 230K LUTs), RTL-level
optimization of the load/MAC pipeline, or system-level changes (speculative
decode, CPU overhead reduction).
