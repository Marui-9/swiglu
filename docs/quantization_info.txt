Quantization in the SwiGLU accelerator
======================================
Revised 2026-10-03. The 2026-05-16 version described a Q6_K path kept under #ifdef ENABLE_Q6K
and Q6_K C-sim tests (both since removed, commit c35a36d), gave the wrong requantization
command, and quoted perplexity and error-budget figures that no measurement in the
repository backs. Those figures are dropped here; see section 7.


1. Overview
-----------
W4A8: weights stay in Q4_K (4-bit nibbles, fp16 d/dmin per 256-element block, 6-bit
sub-block scales and mins), activations are INT8, the MACs accumulate in INT32, and the
output is FP32. Stage-by-stage detail: docs/swiglu_description.md. Where float remains and
why: docs/floats_explanation.txt.


2. INT8 input x (host side)
---------------------------
llama-mods/ggml-cpu.c:2085-2099, once per token (one IP call per token):

    x_scale   = max|x[i]| / 127            (1.0 if x is all zero)
    x_int8[i] = clamp(round_half_away(x[i] / x_scale), -128, 127)

x_scale is written to the XSCALE register (0x54) and multiplies each per-block result in the
IP's reduce step.


3. INT16 X1 / X2 (on chip, fixed scale)
---------------------------------------
X1 = W_gate·x and X2 = W_up·x are stored as INT16 with a fixed range of ±32
(X12_QMAX = 32767, X12_INV_SCALE = 32767/32). Values beyond ±32 clip.

Until 2026-10-23 they were INT8 over ±10 (X12_INV_SCALE = 12.7), as in q4k_final. On the
board that step (≈0.079) rounded 801–2,347 of 8,192 gate·x values per layer to zero, even
though the measured |gate·x| stays ≤ 4.24 and |up·x| ≤ 1.80. The full record, the
measurements and the reason for INT16 over a per-token scale are in
docs/integer_transition.txt.

The gate SiLU(X1)·X2 is requantized per token with a dynamic scale (max|gate|/127),
computed on chip in two passes.


4. The all-Q4_K model
---------------------
The stock Q4_K_M GGUF keeps ffn_down in Q6_K on 8 of 16 layers: 0, 1, 4, 7, 10, 13, 14, 15
(changelog entry 65; docs/gguf-dump_LFM25_Thinking_Q4K_M.txt shows the same pattern in the
Thinking variant's Q4_K_M). The accelerator implements only Q4_K: a Q6_K
block is 210 B (13.125 × 128-bit words) and does not fit the 2D tile layout.

The model used with the accelerator was requantized from Q8_0
(hls_experiments/testblock/changelog.txt, entry 65):

    ./build/bin/llama-quantize --allow-requantize --pure \
        ~/lfm2.5-1.2B-Q8_0.gguf ~/lfm2.5-1.2B-Q4_K_pure.gguf Q4_K

--pure stops llama-quantize from promoting tensors back to Q6_K. Requantizing from the
Q4_K_M file failed with NaN in blk.4.ffn_gate.weight, and plain requantization from Q8_0 is
refused without --allow-requantize. (2026-10-24: the Thinking Q4_K_M,
LFM2.5-1.2B-Thinking-Q4_K_M.gguf, md5 d3cbb0bc..., turned out to be corrupt from blk.4 on,
with NaN and ±3e38 norm weights and PPL 65536; see
scripts/results/kld_ref_20261024/README.md. The non-Thinking Q4_K_M behind the failure
above is no longer at hand, so whether it had the same fault is not verified.) The result is dumped in
docs/gguf-dump_LFM25_Q4K_all.txt: 93 Q4_K + 55 F32 tensors, no Q6_K. Its general.file_type
is still 15 (Q4_K_M), which is why llama-bench labels it "Q4_K - Medium" (628.25 MiB).

The stack enforces Q4_K: lfm2.cpp only emits the fused op when ffn_gate/up/down are all
Q4_K, ggml-cpu.c asserts on any other type, and swiglu.cpp has no Q6_K logic.


5. fp16 d / dmin and subnormals
-------------------------------
Real LFM2 Q4_K blocks contain subnormal fp16 scales (the testbench uses d = 0x00A4 ≈ 9.8e-6).
A conversion that flushes subnormals to zero zeroes the whole block. hls_half did this in
synthesis earlier in the project, and ap_fixed<16,5> (LSB 2^-11 ≈ 4.9e-4) simply cannot
represent such values. swiglu.cpp:53 fp16_to_fp32() therefore converts with integer bit
manipulation:
  - zero          → signed zero
  - subnormal     → normalized by an unrolled 10-step leading-one search
  - exp == 31     → Inf/NaN preserved
  - normal        → exponent rebiased (+112)


6. C-simulation (swiglu_tb.cpp)
-------------------------------
A mock-token sanity test plus four Q4_K tests:
  T1  normal fp16 d, dmin = 0
  T2  subnormal d in W (0x00A4)
  T3  subnormal dmin in V (0x817E)
  T4  non-zero d and dmin in W, V and W_down
Pass criterion per output: |got − expected| ≤ 1e-3 · (|expected| + 1).

The testbench builds its URM data with its own transposer
(transpose_q4k_to_urm_csim), whose header layout matches what swiglu.cpp reads, so C-sim
cannot see a host-side layout error. The host transposer in ggml-cpu.c wrote a different
header layout until 2026-10-04 (README.md, "Driver bugs").


7. Accuracy: what has and has not been measured
-----------------------------------------------
Measured:
  - The C-sim tolerance above, on synthetic weights and activations.
  - 2026-10-23, q4k_final bitstream (INT8 ±10 X1/X2) with the fixed driver
    (scripts/results/fixed_driver_20261023/, README.md "Accuracy"):
      - accelerator output vs build_ffn() per layer, cosine 0.9569–0.9944;
      - the X1/X2 range: |gate·x| ≤ 4.24, |up·x| ≤ 1.80;
      - wikitext-2 PPL HW/CPU 1.081368 ± 0.041650, mean KLD 0.384800, on the same
        all-Q4_K GGUF.
  - 2026-10-23, rebuild_x16 bitstream (INT16 ±32 X1/X2), same GGUF, driver and commands
    (scripts/results/rebuild_x16_20261023/):
      - accelerator output vs build_ffn() per layer (token 2), cosine 0.9930 min / 0.9984
        mean; the IP matches its INT16 emulation at ≥ 0.99980;
      - max |gate·x| 4.27, max |up·x| 2.17 over all logged calls, inside ±32;
      - wikitext-2 PPL HW/CPU 1.034376 ± 0.011605, mean KLD 0.030154.
  - 2026-10-24, rebuild_s2fix bitstream (rebuild_x16 + Stage 2 STABLE fix), same GGUF,
    driver and commands (scripts/results/rebuild_s2fix_final_20261024/): every per-chunk and
    summary value of the KLD run is identical to rebuild_x16's.
  - 2026-10-24, on the PC (scripts/results/kld_ref_20261024/): Q4_K_M (default recipe,
    quantized from the f16/q8_0 GGUF) vs the f16/q8_0 reference, wikitext-2, 24 × 256:
    PPL ratio 1.184104 ± 0.015283, mean KLD 0.153433 ± 0.003147, same top token
    77.264 %.
  - 2026-10-24, on the board (same reference logits, 24 × 256, -t 4, rebuild_s2fix
    bitstream; runs 2-5 of scripts/analysis/kld_ref.sh):
      - allQ4Kffn on the CPU vs f16/q8_0: PPL ratio 1.173772 ± 0.015587, mean KLD
        0.166073 ± 0.003399, same top token 75.951 %;
      - allQ4Kffn through the IP vs f16/q8_0: PPL ratio 1.222886 ± 0.018259, mean KLD
        0.210197 ± 0.004346, same top token 73.852 %;
      - IP vs CPU on allQ4Kffn, 24 chunks: PPL ratio 1.045784 ± 0.006337, mean KLD
        0.034755 ± 0.000749, same top token 88.091 %. At chunk 6 it equals the 6-chunk
        run above (KLD 0.03015).
    So Q4_K on every ffn_down costs KLD +0.013 over the default Q4_K_M mix, and the IP's
    INT8 x/h stages add +0.044 on top of the CPU path (derived).
Not measured:
  - The stock Thinking Q4_K_M GGUF cannot be measured: it is corrupt (above).


8. Q4_0 as an alternative (not evaluated in hardware)
-----------------------------------------------------
GGML block layouts:
    Q4_0: d (fp16), qs[16]                     32 elements, 18 B;  w = (q − 8)·d
    Q4_K: d, dmin (fp16), scales[12], qs[128]  256 elements, 144 B;
          w = d·sc6[sub]·q − dmin·mn6[sub]
A 2048-element row is 1152 B in both formats, so DDR traffic is the same. Q4_0 removes the
sub-block scales, the dmin path and the second accumulator array. Its cost is 8× more
blocks per row (64 per WV row, 256 per down row), each with its own fp16 scale, so the
per-block float reduce runs 8× as often; the tile layout would also change.

The only Q4_0 data is CPU-only: scripts/results/latest_benchmarks/cpu_t<N>_q0.log (661.25
MiB model; T2 decode 1.62 t/s vs 1.66 t/s for the stock Q4_K_M, very likely the corrupt
copy of section 4; its timing stands, its output was never checked).
